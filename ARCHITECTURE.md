# ARCHITECTURE.md — многопоточный Minecraft на Rust

## 1. Цель
Открытая (лицензия MIT) реализация Minecraft: Java Edition **26.3** на Rust:
- **Сервер**, к которому подключаются обычные клиенты Java Edition 26.3 и читающий ванильные миры.
- **Клиент** на Rust (после сервера).
- **Лаунчер** с проверкой, что у пользователя есть легальная копия игры.

Две равноценные цели:
1. **Точность**: поведение совпадает с ванилью, проверяется автоматически.
2. **Скорость**: тики, генерация и сеть масштабируются по ядрам процессора.

## 2. Принципы
- Точность по умолчанию. Вся оптимизация должна проходить parity-тесты. «Быстрый» режим с допустимыми отклонениями — отдельная опция, и только позже.
- Многопоточность без общей изменяемой памяти: данные принадлежат одному потоку/региону, обмен через сообщения.
- Детерминизм: при одинаковом сиде и входах результат один и тот же независимо от числа потоков.
- Windows первой, но платформо-независимый код (платформо-зависимое только в лаунчере).
- Ни байта кода, ассетов или данных Mojang в репозитории.

## 3. Структура workspace
```
crates/
  protocol/     пакеты и кодеки (VarInt, NBT, чанк-формат), версия 26.3
  data/         загрузка реестров из данных пользовательской копии
  world/        чанки, блоки, освещение, чтение/запись формата Anvil (.mca)
  worldgen/     генерация мира (параллельная, rayon)
  ecs/          сущности и компоненты (hecs или bevy_ecs)
  sim/          игровая логика тика: блоки, физика, мобы
  scheduler/    регионы, пул потоков, границы между регионами
  net/          сеть на tokio, вход/выход пакетов
  server/       бинарник сервера, конфиг, команды
  parity/       сравнение с ванильным сервером
  client/       клиент: wgpu + winit (позже)
  launcher/     лаунчер на Tauri (позже)
docs/ PROGRESS.md  DECISIONS.md
```

## 4. Модель потоков (ядро проекта)
- **Сеть (tokio)**: ввод-вывод в отдельном пуле. Входящие пакеты кладутся в очередь нужного региона/игрока, исходящие забираются из очереди отправки. Игровые потоки сетью не блокируются.
- **Регионы**: загруженные чанки группируются в независимые регионы (по близости, как в Folia). Каждый регион тикается отдельной задачей в пуле потоков с кражей работ (work-stealing). Регион владеет своими чанками и сущностями.
- **Границы**: действия, затрагивающие соседний регион (взрыв, поршень, перемещение сущности), отправляются сообщением и применяются на границе тика в детерминированном порядке (по ID региона, затем по номеру события). Если регионы сближаются, они объединяются; если расходятся, делятся.
- **Тяжёлые задачи** (генерация чанков, освещение, сжатие, запись на диск): отдельные пулы (`rayon`), результат возвращается в регион и применяется в начале следующего тика.
- **Тик**: 20 TPS (50 мс). Главный планировщик запускает тик всех регионов, ждёт барьер, применяет межрегиональные сообщения, рассылает пакеты.
- Ожидаемое масштабирование проверяется бенчмарком на 1/2/4/6/12 потоках (тестовое железо: Ryzen 5 2600X, 6 ядер/12 потоков).

## 5. Данные и совместимость
- Реестры (блоки, предметы, сущности, биомы и т.д.) и их ID **не хранятся в репозитории**. При первом запуске `data` вызывает штатный генератор данных из jar-файла игры пользователя и сохраняет результат локально (папка вне репозитория, в `.gitignore`).
- Ассеты клиента (текстуры, звуки, модели) берутся из установленной у пользователя игры.
- Формат мира: читаем и пишем ванильный Anvil, сохраняем обратную совместимость с ванильным сервером.
- Parity-тесты (`crates/parity`): запускают ванильный сервер 26.3 (jar от пользователя) и наш с одним сидом и одинаковыми входами, затем сравнивают: сгенерированные чанки, пакеты, результаты тиков, команды. Расхождение = баг у нас.

## 6. Клиент (после сервера)
`wgpu` (Vulkan/DX12 на Windows, GTX 1660 Super подходит) + `winit`. Загрузка чанков, меш чанков в параллельных задачах, текстуры из копии игры пользователя. Рендер и игровая логика клиента в разных потоках.

## 7. Лаунчер
Tauri v2 (Rust + веб-интерфейс):
- Вход через аккаунт Microsoft по официальному потоку (Microsoft → Xbox Live → XSTS → Minecraft Services).
- Проверка владения игрой через официальный API. Нет копии — запуск запрещён. Никаких обходов.
- Находит установленную Java Edition, проверяет версию 26.3, подготавливает данные (раздел 5).
- Скачивает и обновляет сборки из GitHub Releases, проверяет контрольные суммы.

## 8. Этапы (milestones)
Каждый этап считается выполненным, только когда выполнено условие «Готово, когда».

| # | Этап | Готово, когда |
|---|------|---------------|
| M0 | Каркас: workspace, CI (fmt, clippy, test), README, лицензия MIT, `.graphifyignore`, `docs/` | CI зелёный на GitHub |
| M1 | Протокол: handshake, status | Сервер виден в списке серверов клиента 26.3 |
| M2 | Вход (login) и вход в пустой мир | Клиент заходит и не вылетает |
| M3 | Чтение ванильного мира, отправка чанков | Игрок видит мир из ванильного сохранения |
| M4 | Тик-цикл, регионы, движение игроков | Несколько игроков двигаются, TPS=20, регионы тикаются параллельно |
| M5 | Ломание и установка блоков, освещение, чат, команды | Parity-тесты блоков и освещения зелёные |
| M6 | Генерация мира | Чанки совпадают с ванильными для набора сидов |
| M7 | Сущности и мобы | Parity-тесты сущностей зелёные |
| M8 | Бенчмарки против ванильного сервера | Опубликованный отчёт TPS по числу игроков и потоков |
| M9 | Клиент: окно, рендер чанков, управление | Игрок ходит по миру в нашем клиенте |
| M10 | Лаунчер: вход, проверка копии, обновления | Установка и запуск с чистой машины |

После M8 владелец проекта решает, продолжать ли, по результатам бенчмарков.

## 9. Бенчмарки в CI
Каждый PR прогоняет сценарий «N игроков, M мобов, K чанков» и сравнивает TPS и время тика с предыдущей версией. Регресс больше 5% помечает PR красным.

## 10. Риски
- Протокол и логика 26.3 новые, часть деталей придётся добывать через parity-тесты, а не по документации.
- Строгая совпадаемость с ванилью и многопоточность конфликтуют: любое отклонение фиксируется в `docs/DECISIONS.md`.
- Мелкая ИИ-модель ошибается в больших задачах: держи шаги маленькими, всегда запускай тесты.
