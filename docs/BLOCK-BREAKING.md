### 1.4 Что из этого установлено, а что нет

**Установлено:** id пакетов и направления; packed-pos BE 8 байт; `player_action`
= action byte + pos + face byte + sequence varint; `block_changed_ack` = тот же
sequence; `block_update` = pos + state varint; `block_destruction` = entityId +
pos + stage byte (в трейсах 0..13; `0xFF` — сброс, §1.7); `level_event` =
event int32 BE + pos + data int32 BE (+1 неясный байт); `add_entity` предмета
типа 72 у обеих сторон.

**Поведенчески выведено из трейсов (не из packets.json):** action `0x00` —
старт; `0x03` — завершение (следом `block_update` state 0 и `block_changed_ack`
с тем же sequence); `0x02` — прерывание (следом `block_changed_ack` с seq `00`,
блок не удаляется). В creative (1.5) действия `0x03`/`0x02` не встречаются
вообще — только `0x00` на каждый блок.

**Не установлено:** официальные имена/значения enum action (в `packets.json`
только id); смысл `face`-байта (встречены `0x01` и `0x02`; попадание в верхнюю
грань дало `0x01`, в северную — `0x02`, что согласуется со стандартным порядком
«0=низ, 1=верх, 2=север…», но это вывод поведения, не факт); смысл `data` у
`level_event` 2019/2020; лишний байт `level_event`; раскладка
`set_entity_data` предмета.

**Факты creative:**

- Каждый блок — отдельный `player_action` `0x00` (start) со своим `face` и
  `sequence`; сервер отвечает **на каждый start** `block_update` state 0 +
  `block_changed_ack` с тем же sequence. `0x03` (finish) и `0x02` (abort)
  в creative **не встречаются** — ваниль ломает мгновенно на старте.
- `punch` (пустой) сопровождает атаки; в creative он не «взмах копания», а
  пара к каждому новому блоку.
- **Что видел наблюдатель B** (по часам B): `level_event` ×2 и
  `swing_animation` ×2 (`4c 000106`, entity 76) и `block_update` state 0 ×2 —
  **перед break-обновлением**. **Не приходят**: `block_destruction` (5),
  `sound` (119), `block_changed_ack`, `add_entity` предмета (в creative дропов
  нет).
- **`level_event` 2001**: `000007d1 <pos:8> 000001c2 00` — event int32 BE
  (2001 = разрушение), pos, data int32 BE = `450`. По `blocks.json` state 450 =
  `minecraft:dark_oak_leaves` (distance 4) — **data 2001 = block state id
  ломаемого блока**. Сходится со старым трейсом S3: там 2001 data = `9`, state 9

  Формат подтверждён 4-м и 5-м семплами; лишний байт `00` в конце — прежний
  вопрос.
- **Почему A не упал**: ваниль сломала два листа тёмного дуба на y=143 рядом со
  спавном (луч при dy 400 идёт под ~60–70°, не строго вниз, и проходит в углубление

  сценария «A должен упасть» был неверным предположением и переписан на
  «crosshair сменил цель».
- **Tap не работает** (факт, два прогона 0918 и 0932): одиночный клик attack

  отправляет **ни одного** пакета (ни `player_action`, ни `punch`). Пакеты даёт
  только удержание (≥~700 мс в 0932: 2 блока). Причина на стороне клиентского
  мода/ванильного клиента — не установлено (гипотеза в 5.2).

### 1.6 Что реализовано (шаг 14c): creative, `level_event` 2001, порядок

Код: `crates/protocol` (`LevelEvent`, id 47, `EVENT_BLOCK_BREAK = 2001`,
`TRACED_TRAILING = 0x00`), `crates/net/src/game/block_action.rs`
(`broadcast_break`, creative start → finish), `ServerMessage::LevelEvent`.
Тесты: побайтные в `protocol` (S3 и S9 hex), 10 тестов `block_action`
(3 новых creative), плюс живой прогон.

- **Creative = mode 1.** `player_action 0x00` (start) в creative идёт тем же
  путём, что `0x03` (finish) в survival: блок проверяется в `ChunkStore`, при
  успехе ставится `0`, затем `broadcast_break` и `block_changed_ack`.
  `0x02` (abort) и start в survival по-прежнему только подтверждаются. Ветки
  `0x03`/`0x02` в creative из S9 не встречались и отдельно не обрабатываются.
- **`level_event` (2001) побайтно** (payload, id пакета 47):
  `000007d1 | <packed pos:8> | 000001c2 | 00`
  - `000007d1` — int32 BE `2001` (событие «разрушение блока»);
  - `<packed pos>` — `Position` в том же порядке, что `block_update`;
  - `000001c2` — int32 BE `450` = **state id сломанного блока, прочитанный из
    `ChunkStore` ДО удаления** (S3: `9` = `grass_block`, S9: `450` =
    `dark_oak_leaves`);
  - хвостовой `00` — **смысл не установлен**; гипотеза: флаг «глобальное
    событие» (у ванильного `level_event` это поле существует). Байт отправляется
    константой `TRACED_TRAILING`.
- **Порядок на проводе:** `level_event` наблюдателям (копающий исключён) →
  `block_update` state `0` всем, включая копающего → `block_changed_ack`
  копающему. Это порядок S3/S9; чек S9 (`ordered=True`) проверяет его попарно,
  потому что два блока дают чередование `2001, air, 2001, air`.
- **`level_event` теперь и в survival** (S3): раньше `block_action` слал только
  `block_update` + ack. `2019`/`2020` (эффекты во время копания) и
  `block_destruction` **не отправляются**; трещин/дропов нет.
- **Живой прогон на нашем сервере** (`2026-11-16_1233`, target `ours`,
  `-OursGameMode 1`): 5/5 PASS. B получил те же байты, что ваниль:
  `000007d1 0000183ffffe208f 000001c2 00` → `0000183ffffe208f 00`, затем то же
  для второго блока (z = −31). Совпадение с S9 — байт-в-байт.
- **Ограничения:** аудитория — все игроки (M4 — один регион); правило «кто
  видит чанк» не реализовано (§4.1). Свет не пересчитывается (§4.3).

Циклы `1,3,5,сброс` в 1606 — это три «тапа» по блоку (нажатие-отпускание):
копание стартует, сервер успевает прислать 3 стадии, клиент отпускает атаку →

**Что из этого следует (факты, не гипотезы):**

1. **Диапазон стадий шире 0..9:** в трейсах есть 10, 11 и **13**. Все пакеты
   одной позиции приходят от одного копающего (entityId 826 в 1606, 51 в 1303;
   второго копающего нет). Запись «stage 0..9» в §1.3/§1.4 была неполной.
2. **`0xFF` — это сброс, а не только «успешный финал»:** он приходит и после
   прерывания (2001 нет, `block_update` нет, блок остался).
3. **Стадии шлются только при изменении значения**, не каждый тик: у
   dark_oak_log (60 тиков) пакеты идут каждые ≈298 мс ≈ 6 тиков; у листвы
   (6 тиков) — почти каждый тик, отсюда «рваные» интервалы 20...216 мс из §1.3.
4. **Форма последовательности** — `stage(k) = floor(10·d·k)` при постоянном
   `d` (прогресс за тик): листва `1,3,5,6,8,10,11,13` = `floor(1.67·k)`,
   k = 1..8; бревно `0..10` с шагом ≈6 тиков = `floor(0.164·k)`.
5. **Прогресс не ограничен единицей:** у листвы последняя стадия 13 ⇒ прогресс
   ≈1.3, и только потом сброс; `block_update` в воздух приходит **после**
   сброса (1606: stage 13 @4250.2, сброс @4268.9, `block_update` state 0
   @4291.6). Значит сервер **не ломает блок сам по достижении прогресса 1.0**:
   блок убирает `player_action 0x03` от клиента (§1.2), а прогресс нужен только
   для трещин.
6. **Длительность копания в тиках — это клиентский таймер:** ≈16 тиков для
   grass_block, ≈15 для dirt, ≈6 для листвы, ≈60 для dark_oak_log (шаг
   стадий у бревна ровно 298 мс ⇒ тик 50 мс в этих прогонах).
7. Прогресс в момент сброса (по `d` из п.4) лежит в диапазоне **0.94...1.36**:
   grass успевает сброситься чуть раньше серверной единицы, листва — на
   ≈2 тика позже. Это и есть наблюдаемый разброс для допуска проверки времени

| stone (копался только в 16a.4 live) | 1 | 1.5 | 45 | 150 у клиента (§4.3.2) |

Формула `progress += speed/hardness/30` за тик (T = 30·hardness при speed 1.0)
**подтверждена на всех четырёх блоках**: листва, dirt и бревно совпадают точно,
а grass (0.6 → 18) в таблице выглядит как 16 только потому, что здесь он
измерен от **первого пакета стадии**, а не от старта копания. Оракул ниже
(§1.7.1) снимает этот сдвиг, и §1.8 разбирает его по данным (включая
`on_ground` и пустую руку) — это измерение, а не другая скорость клиента.

#### 1.7.1 Оракул интервалов стадий (16a.4 п.4)

Модель: стадия 0 — на тике 1, стадия `k ≥ 1` — на тике `ceil(k·T/10)`,
`T = 30·hardness/speed`. У прокси на каждое копание свой постоянный сдвиг
доставки (наблюдатель начинает свой отсчёт со своего входа, а пакеты идут
пачками), поэтому оракул вычитает медиану остатков `модель − наблюдение` по
стадиям этого копания и требует после сдвига: каждая стадия ±1 тик, каждый
**переход** ±1 тик и весь span (первая→последняя стадия) ±1 тик.
Регрессионный тест — `crates/net/src/game/dig_oracle_tests.rs` (10 копаний,
5 тестов).

| копание | T | сдвиг | худшая стадия | худший переход | span | finish−T |
|---|---|---|---|---|---|---|
| 1303 dark_oak_leaves (97,144,−34) | 6 | +1.64 | 1: 0.64 | 1→3: 0.63 | −0.67 | −1.00 |
| 1303 dark_oak_leaves (97,144,−33) | 6 | +1.55 | 1: 0.55 | 1→3: 0.36 | −0.63 | +0.01 |
| 1303 dark_oak_leaves (98,144,−33) | 6 | +1.63 | 1: 0.63 | 1→3: 0.63 | −0.65 | +0.01 |
| 1451 oak_leaves (98,138,−22) | 6 | +1.85 | 1: 0.85 | 1→3: 0.68 | −0.85 | −0.76 |
| 1451 oak_leaves (98,137,−22) | 6 | +1.72 | 1: 0.72 | 1→3: 0.67 | −0.74 | +0.01 |
| 1606 oak_leaves (97,138,−22) | 6 | +1.59 | 1: 0.59 | 1→3: 0.58 | −0.32 | +0.41 |
| 1606 oak_leaves (97,137,−22) | 6 | +1.68 | 1: 0.68 | 1→3: 0.70 | −0.68 | −0.38 |
| 1636 grass_block (95,127,−22) | 18 | +1.62 | 0: 0.62 | 0→1: 0.65 | −0.64 | −1.62 |
| 1636 dirt (95,126,−22) | 15 | +1.47 | 0: 0.47 | 0→1: 0.75 | −0.47 | +0.10 |
| 1644 grass_block (93,123,−22) | 18 | +1.61 | **2: 2.33** | 1→2: 2.32 | −0.67 | −1.93 |

Итог: 9 копаний из 10 укладываются в ±1 тик по стадиям (худшее 0.85),
переходам (0.75) и span (0.85) после одного сдвига на копание. Сдвиг у всех
копаний 1.47...1.85 тика — первый пакет стадии приходит примерно через полтора
тика после «тика 1» модели, и именно это (а не длительность копания) делало
grass «16 тиков» в §1.7. Десятое копание (1644) имеет **задержку доставки**:
стадия 1→2 идёт 4.32 тика вместо 2, и оракул обязан её показать — тест
`the_1644_grass_dig_flags_its_delivery_stall` требует отклонение > 2 тиков,
остальные 9 стадий того же копания лежат в ±1 тик. Это единственное
исключение в данных, помечено, а не спрятано.

**Важно для реализации (16a.3):** `hardness = 0` — мгновенное ломание (как
creative), `hardness < 0` — блок не ломается вообще; экспорт без
`handSpeed` допустим (загрузчик берёт 1.0). Первый экспорт дал `handSpeed =
0.2` у всех состояний — клиент ещё падал после входа, а игра делит скорость
копания на 5 в воздухе; команда теперь отказывается работать не на земле
(`fix: refuse an airborne hardness export`), файл перегенерирован.

### 1.8 Разрыв grass в 2 тика: измерение, а не скорость клиента (16a.4 п.2)

Вопрос: `hardness.json` даёт grass 0.6 ⇒ 18 тиков, а §1.7 мерил 15.9/16.1.
Проверка гипотез **по данным** (не по памяти):

1. **«Скорость клиента зависит от земли/воды».** В обоих прогонах копающий
   стоял на земле: serverbound `move_player_*` перед копанием и после него
   несут `flags = 0x01` (`on_ground`, бит 0 —
   `crates/net/src/game/movement.rs`). 1636: старт 40463.7 по (95,127,−22), в
   40543 флаг `0x01` на y = 128.0, а падение (`0x00`, y = 127.92) начинается
   только после слома блока — игрок стоял ровно на этом блоке. 1644: старт
   41093.6, ближайшие пакеты 40693.8 и 41546.5 — `on_ground = true` на
   y = 126.0 без движения. В воздухе/воде игра делит скорость на 5: grass
   занял бы ≈90 тиков, а не 16. Гипотеза не подтверждается.
2. **«Другая скорость без правильного инструмента».** Ни в одном из двух
   трейсов нет serverbound пакета смены предмета (только clientbound
   `set_held_slot`/`container_set_content` при входе). Штраф «нет правильного
   инструмента» — делитель 100: для grass это 60 тиков (`0.6·100`), вчетверо
   больше наблюдаемого. Гипотеза не подтверждается; сам штраф существует
   (виден на камне, §4.3.2).
3. **Остаётся измерение.** Способ §1.7 — от первого пакета стадии до `0xFF`.
   Оракул (§1.7.1) показывает, что первый пакет приходит на 1.5–1.9 тика позже
   «тика 1» модели, и с этим сдвигом все 10 стадий grass (0..9) ложатся в
   ±0.62 тика от T = 18; span 15.36 — это span стадий, а не копание. Счёт
   `client_tick_end` между start и finish даёт 17 — ровно T−1, т.е. попадает
   в ±1 тик фазы границы тика.
4. **Прямое подтверждение в live-прогоне** `2026-11-17_0110` (наш сервер): то
   же первое копание после загрузки чанка пришло на 678 мс = 13.56 тика при
   T = 18 — прокси отдал пачку пакетов, и `read_ms` сжал интервал; счётчик
   `client_tick_end` того же копания — 17. То есть стена-время стенда врёт на
   несколько тиков, а клиентское время — нет.

**Вывод:** `T = 30·hardness` верна и для grass (18 тиков); «2 тика» — это
сдвиг доставки первого пакета ≈1.5 тика плюс граница тика ±1. Пометка
`unverified for grass` снята. Для практики важно, что живая проверка finish не
должна опираться на сжатое стеной время (§4.3.2: допуск и отказы).

## 3. Где живут блоки (как менять и как это увидят вошедшие позже)

Факты (с файлами):

- `crates/world/src/chunk.rs` — `Chunk`/`Section`, `check_sendable`
  (DataVersion → Status ∈ {`minecraft:full`, `minecraft:initialize_light`} →
  есть свет); `crates/world/src/wire.rs` — `Chunk::level_chunk` собирает
  heightmaps/sections/block_entities/light; `crates/protocol/src/packets/chunk.rs`
  — wire-структура.
- `crates/net/src/chunks.rs` — `window`, `window_difference`, `ReadyChunks`
  (индекс O(1)); `crates/net/src/loader.rs` — `ChunkSource`/`Loader`;
  `crates/net/src/connection/play/batch.rs` — запись батча.
- **Кеш:** `crates/net/src/store.rs` — `ChunkStore` (шаг 13a): один
  `RwLock<Arc<ReadyChunks>>`, единственный писатель — игровой поток;
  соединение на входе и на сдвиге окна берёт `snapshot()`. Кеш шаблона
  (`TemplateWorld`) остаётся источником стартового батча, но живой мир после
  прогрева — это `ChunkStore`.
- **Путь изменения блока есть (шаг 13b):** `ChunkStore::set_block` пересобирает
  только изменённый чанк и публикует новый снимок; `player_action` (41)
  декодируется в `crates/protocol`, доезжает до тика как
  `ToGame::BlockAction` и применяется в `net::game::block_action`
  (`crates/net/src/game/block_action.rs`). Всё — только в памяти.
- **Владения чанками в регионе нет:** `Region`/`Scheduler`
  (`crates/net/src/game/region.rs`, `scheduler.rs`) владеют только игроками;
  блоки живут в общем `Arc<ChunkStore>`, который тик получает через
  `GameConfig.store`.

**Освещение.** Движка света нет: `crates/world/src/wire_light.rs` копирует
готовые `SkyLight`/`BlockLight` из NBT, а секцию без сохранённого sky light
отправляет как 15 (`0xFF`). Решение — `docs/DECISIONS.md` §141/89/105–108/164–186.
Минимальная версия для удаления блока: пересчитать свет нельзя без движка,
поэтому первая версия может (а) не трогать свет вовсе (визуально — «дыра со
старым светом») и (б) быть помечена как известное ограничение; полноценное
освещение — этап M5 (`ARCHITECTURE.md`: «M5 = блоки + свет»).

## 3.5 Что реализовано (шаг 13b)

**Провод (побайтно, эталон — S3 `2026-11-14_1644`).** Все три типа — в
`crates/protocol/src/packets/play.rs`, тесты `player_action_roundtrips_the_s3_break`
и `block_update_and_ack_roundtrip_the_s3_break`:

| Пакет | id | payload (hex из трейса) |
|---|---|---|
| `player_action` (serverbound) | 41 | start `00 0000177ffffea07b 01 01`, finish `03 0000177ffffea07b 01 02` |
| `block_update` (clientbound) | 8 | `0000177ffffea07b 00` |
| `block_changed_ack` (clientbound) | 4 | `01` (start), `02` (finish) |

**Путь.** Соединение (`crates/net/src/connection/play/mod.rs`) распознаёт id 41,
декодирует и шлёт `ToGame::BlockAction`; игровой поток
(`crates/net/src/game/mod.rs`) вызывает `block_action::apply`; результат —
`ServerMessage::BlockUpdate` / `ServerMessage::BlockChangedAck`, которые
соединение пишет, резолвя id через `ids.id(...)`.

**Поведение.**

- start (`0x00`) и abort (`0x02`) → только `block_changed_ack` с эхом sequence;
  блок не меняется.
- finish (`0x03`): блок читается из `ChunkStore`. Если чанк загружен и блок не
  воздух — пишется `state 0` (`AIR_STATE`), `block_update` уходит **всем**
  игрокам (копающему тоже), затем ack копающему — порядок как в трейсе §1.2.
- Отказ (**гипотеза**, трейса нет): если блок уже воздух — копающему уходит
  `block_update` с реальным состоянием и ack; если чанк не загружен — только
  ack (нечего послать). Никаких иных игроков это не касается.
- `store == None` (тесты, bench, мир не прогрелся) — только ack.

**Тесты.** `crates/net/src/game/block_action_tests.rs` (7): успех и порядок
«update → ack», наблюдатель получает только update; поздний вход читает
изменённый снимок (плюс `connection::play::tests::
a_sender_after_a_block_change_reads_the_new_block`); воздух; отсутствующий
чанк; start/abort; отсутствие store; путь через `ToGame::BlockAction`.

**Ограничения (не реализовано и почему).**

- **Creative-клиент у нас не получит мгновенного ломания**: ваниль в creative
  ломает блок на каждый `0x00` (1.5), а наша реализация на start отвечает только
  ack — блок меняется лишь по `0x03` (survival-модель). Для creative-клиентов
  нужен game mode на сервере и правило «start в creative = destroy» (стадия 1,
  байты подтверждены 1.5).

- **Свет не пересчитывается** — движка нет (п. 7 `MECHANICS.md`). Шлёт ли
  ваниль после `block_update` пакет света — **не установлено**.
- **Трещины, звук, частицы, предмет, `block_destruction`/`level_event`/
  `add_entity`** — не реализованы (стадии 3–5). Байты известны, но не пишутся.
- **Нет серверного таймера копания, твёрдости и проверки дальности** — сервер
  доверяет клиенту (стадия 2, §4.2; п. 14 `MECHANICS.md`).
- **Аудитория `block_update` — все игроки**, а не «у кого загружен чанк»:
  M4 держит один регион, правило видимости — долг (§4.1).
- **На диск не пишется:** после перезапуска блоки возвращаются (стадия 7).

## 4. Стадии

Размер: **A** (углы `add_entity`) — маленький, **B** (присед/спринт) — средний,
**C** (взмах наблюдателям) — маленький (только проводка сообщения + payload).
Проверка в каждой стадии: побайтный юнит-тест против hex из трейса + live-ручная
проверка двух клиентов через `tools\testclient\client.bat` с записью mcproxy
(см. 4.0).

### 4.0 Про проверку (важно)

- **Автоматический S6/S3-dig сейчас красный по причине стенда** (записано
  владельцем; причина не исследована): в авто-прогонах клиент не считает
  удержание атаки копанием (`player_action` 41 = 0 в трейсах ours), а S6
  проверяет только то, что `observe` вернул снимок.
- Поэтому проверять ломание будем: (1) **юнит-тестами побайтно** (эталон — hex
  из 1.2/1.3); (2) **ручной live-проверкой владельца**: два клиента
  (`client.bat`) или мод-клиенты через mcproxy, копание вручную, разбор
  трейса; (3) когда стенд перестанет врать — сценарием автотеста.
- Есть эталонные «одна сессия, один блок» прогоны для сверки (см. 1.3).

  sequence`; clientbound копающему `block_update` (8) `pos + state 0` и
  `block_changed_ack` (4) = sequence; остальным — `block_update` (8) по той же
  позиции. `block_destruction` не нужен (мгновенно).

  «кто видит чанк»; отсутствие света (4.3).

### 4.3 Стадия 3 — трещины (`block_destruction`), твёрдость

**Статус: механика выведена из данных (16a.2), код — 16a.3, оракул и live

Данные: 11 сломанных блоков и 6 прерванных копаний в 5 прогонах, §1.7.

- **Пакеты:** `block_destruction` (5) `entityId varint + packed pos + stage byte`.
  `stage` = **`floor(10·progress)` без ограничения сверху** (наблюдались 10, 11,
  13), `0xFF` — **сброс** (и после финиша, и после прерывания). Копающему не
  шлётся (§1.3), наблюдателям — только при изменении значения.
- **Модель (выведена, §1.7 пп.3–5):**
  - сервер ведёт `progress` на пару (игрок, позиция): +`speed/hardness/30` за
    тик, без клиппинга (`speed` пустой рукой = 1.0 — из `hardness.json`);
  - каждый тик, если `floor(10·progress)` изменился, — рассылка стадии всем,
    кроме копающего;
  - `player_action 0x00` — старт (с этого тика идёт прогресс), `0x02` — сброс,
    `0x03` — блок убирается (`block_update` + ack), после чего сброс;
  - **сервер не ломает блок сам** по прогрессу ≥ 1.0: в 1606 стадии 11 и 13
    пришли уже после прогресса 1.0, `block_update` — только после `0x03`.
- **Работа (16a.3):** состояние копания (позиция, старт, прогресс) в тике
  региона; `block_destruction` в `crates/protocol`; рассылка стадий
  наблюдателям; сброс по `0x02`; при `0x03` — проверка времени по прогрессу с
  допуском (наблюдаемый разброс 0.94…1.36, §1.7 п.7) и, если не проходит, —
  откат реальным состоянием (`block_update`), помеченный как гипотеза;
  creative по-прежнему мгновенный (§4.1).
- **Проверка:** побайтные тесты стадий по трейсам §1.7 (в т.ч. значения 10/11/13
  и сброс после прерывания); оракул интервалов (тики ±1, `dig_oracle_tests`);
  live A/B 2026-11-17 (§4.3.2): A ломает 10 блоков четырёх твёрдостей в
  состояниях земля/присед/вода/воздушная стойка, B видит стадии, `0xFF`, 2001
  и воздух, ни одного отказа.
- **Риски:** grass больше не расходится — «16 тиков» были сдвигом доставки
  (§1.8); камень пустой рукой клиент копает 150 тиков, а модель даёт 45 —
  трещины у наблюдателя идут в 3.3 раза быстрее (полная стадия к ~44 тикам

  гипотезой и может отклонить честный финиш после догона тиков клиента
  (§6 п.8); аудитория стадий — все игроки (M4, как в §4.1).
- **Размер:** большой (таймер-механизм + новая рассылка), но без дропов/звука

#### 4.3.1 Что реализовано (шаг 16a.3)

- **Пакет:** `BlockDestruction` (id `0x05`, `KEY`) в `crates/protocol`,
  `entityId varint + packed pos + stage u8`; `RESET = 0xFF`. Побайтные тесты —
  четыре payload'а из трейсов §1.3 (`330000187ffffde09001`,
  `ba060000187ffffea08d01`, `ad08000017fffffea07f00`,
  `8a080000177ffffea07b00`).
- **Состояние:** `DigState` у `Player` (`position`, `progress`, `step`, `stage`,
  `ticks`) — одно копание на игрока, как в ванили. Таймер включается только для
  survival и только когда `hardness_report` даёт `hardness > 0`; `hardness = 0`
  — мгновенно (доверяем finish), `hardness < 0` — неломаемо (finish
  отклоняется), состояния нет в отчёте / отчёта нет — прежнее доверие клиенту.
- **Тик:** `game::dig::tick` идёт **после** `scheduler.tick`, поэтому игрок,
  сменивший регион в этом тике, продвигается уже в новом. За тик:
  `progress += step`, затем `stage = floor(progress·10)` **без клиппинга**
  (сверху ограничено 254, чтобы не столкнуться с `0xFF`); пакет — только если
  байт изменился. `stage = None` до первого тика: медленные блоки (dirt,
  grass, бревно) начинают со стадии 0, листва (6 тиков) — со стадии 1, как в
  трейсах.
- **f32, не f64:** прогресс и шаг хранятся в `f32` — игра накапливает прогресс
  float'ом, и шесть шагов `1/6` в `f32` дают ровно тот наблюдаемый переход на
  стадию 10; сумма тех же шагов в `f64` — 0.9999999999999999 и стадия 9.
- **Сбросы `0xFF`:** на `0x02` (abort) и при остановке копания (смена блока,
  отказ, выход игрока); на успешном finish — **до** `level_event 2001` и
  `block_update`, как в трейсе 1606 (стадия 13 @4250.2 → `0xFF` @4268.6 →
  2001 @4269.0 → air @4291.6). Остановка копания при выходе игрока добавлена
  отдельно (`ToGame::Quit`).
- **Проверка времени на finish:** при допуске `t` финиш проходит, если
  `progress + t·step >= 1.0`; иначе — отказ: реальное состояние уходит
  копающему (`block_update`), наблюдателям только `0xFF`, блок остаётся.
  Значение по умолчанию `t = 3` (мягкий вариант §6 п.8), настройка
  `GameConfig.dig_tolerance_ticks: Option<u32>`; `None` — проверку выключить,
  оставив стадии. **Гипотеза** (в трейсах отказа нет).
- **Состояние копающего (16a.4 п.3b):** проверка finish **пропускается**,
  если копающий в воздухе (`on_ground = false`) или его ноги в воде
  (`ChunkStore` в позиции ног даёт воду). Проверка — это **нижняя** граница
  времени, поэтому честное копание в воздухе/воде (клиент там медленнее)
  прошло бы её и без пропуска; пропуск — страховка от обратной ошибки, когда
  догон тиков клиента сжимает финиш ниже границы (live `2026-11-17_0131`:
  листва 2.65 серверных тика вместо 6). Это вариант (b) §6 п.8.

  Live-данные уточняют само правило: делитель ×5 даёт **не вода под ногами**,
  а `on_ground = false` и глаза в воде. Dirt, стоя на земле с ногами в воде и
  сухими глазами, — 14 тиков при T = 15 (штрафа нет). Камень в яме под водой
  (сначала всплывание с `on_ground = false`, затем стойка с глазами в воде) не
  сломан за 481 тик при 151 на земле (два прогона) — ≥3.2×, согласуется с ×5
  (§4.3.2). Пропуск по ногам в воде покрывает случай глаз в воде (там ноги
  тоже в воде) и просто шире правила на один безвредный случай. **Настоящее
  расхождение — темп стадий:** мы шлём их по земному `speed/hardness/30`, а
  ваниль замедляет трещины в этих состояниях; live-проверка с завершённым
  воздушным копанием не удалась (стойка приземляется до старта), поэтому
  воздушный темп — только юнит-тесты, а водный множитель остаётся гипотезой
  ×5 без завершённого копания. Это долг: для воды нужен трейс копания до
  конца, для воздуха — стенд, который жмёт атаку до проверки прицела.
- **Тест (16a.4 п.3c):** `an_airborne_finish_is_trusted_and_breaks_the_block`,
  `a_finish_with_the_feet_in_water_is_trusted` и
  `the_same_pose_on_dry_ground_is_still_refused` — доверие в воздухе/воде не
  отключает проверку на земле.
- **Аудитория:** стадии и `0xFF` — всем, кроме копающего; сам копающий получает
  свои `block_changed_ack` и (на finish) `block_update`. `level_event` 2001 —
  по-прежнему только наблюдателям.
- **Сделано в 16a.4:** оракул интервалов (`dig_oracle_tests`) и live A/B
  (§4.3.2). **Не сделано (16a.5):** звук и частицы (`level_event` 2019/2020) —
  их отдельный вопрос: в прогоне 1644 они дошли и до наблюдателя, что
  расходится с комментарием `LevelEvent` («только копающему»); решится в
  16a.5.

  стойке (камень платформы под вынутой землёй) даёт ответ на вопрос про
  погружение: после слома игрок ~46 тиков тонет в яме (`on_ground = false`),
  затем стоит на дне, а его глаза (`y + 1.62`) оказываются в водном блоке;
  камень **не сломан за 481 тик** (на земле — 151) и прерван по отпусканию
  клавиши, в повторе 0149 — 475 тиков. Это ≥3.2× и согласуется с ×5
  (755 тиков), т.е. штраф включают **не ноги в воде**, а `on_ground = false`
  или глаза в воде (два делителя по 5 из `Player.getDestroySpeed`). Наши
  стадии в этой позе шли по земному шагу: B получил 0..106, хотя клиент не
  прошёл и двух третей. Это тот же долг, что у камня (§4.3 ниже), но
  завершённого копания под водой нет — множитель остаётся гипотезой ×5.

- **Воздушная стойка на земле:** прицеливание на стенде занимает ≈250 мс,

  прогона начали копание с земли; воздушное состояние live не проверено,
  только юнит-тестами. Финиш 154.5 мс = 3.09 серверных тика при T = 6 был
  принят **на границе** допуска (0.515 + 3·0.1667 = 1.015).
- **Отказов в этих прогонах нет:** все 10 `block_update` у B — state 0;

  прогоне `2026-11-17_0131` первое копание (та же воздушная стойка, листва,

  чанка «догнал» 11 тиков за 1.4 мс, прогресс 0.44 + 0.5 < 1 — сервер отказал,
  вернул копающему `block_update` 294, блок появился снова, игрока подтолкнуло
  вверх, и он копал заново. Это п.3c: юнит-тесты «своевременный финиш не
  откатывается» проходят, но live-проверка может отклонить честное копание
  при расхождении часов клиента и сервера (§6 п.8). Обход стенда: пауза после
  прицеливания и первое копание в состоянии, где финиш доверяется; в игре
  владелец может поставить `dig_tolerance_ticks = None`.

## 5. Гипотезы (помечены, не факты)

1. **Блок у копающего исчезает от клиентского прогноза** (факт владельца: можно
   даже ходить сквозь). До шага 13b сервер 41 игнорировал, и после перезахода
   блоки возвращались — этим факт и подтверждался. Теперь сервер блок меняет
   сам, но только в памяти: возврат после перезапуска сервера остаётся.
2. **Tap attack не отправляет пакетов** (обновлено шагом 13c): S9 показал, что
   прицел был на блоке (`hitType=BLOCK`), а одиночный клик всё равно не дал ни
   `player_action`, ни `punch` — два прогона подряд. Значит дело не в промахе
   прицела (как предполагалось для S6), а в самом пути тапа: release тапа,
   по-видимому, обрабатывается раньше, чем клиентский тик успевает запустить
   атаку. Удержание работает всегда. Проверка — разбор кода пути атаки
   ванильного клиента / тест с разной длительностью тапа.
3. ~~**В creative `block_destruction` не шлётся**~~ — подтверждено (шаг 13c,
   1.5): creative-ломание — это `player_action 0x00` → `block_update` +
   `block_changed_ack` на каждый блок, наблюдателю — `level_event` 2001 +
   `swing_animation`; `block_destruction` нет.
4. ~~**Звук ломания идёт через `level_event` 2001**~~ — усилено (шаг 13c):
   `sound` (119) не приходил при ломании ни в survival (S3), ни в creative (S9);
   `data` у 2001 — block state id ломаемого блока (`9`=grass_block, `450`=
   dark_oak_leaves). Клиент сам подбирает звук/частицы по state id.
5. **Ответ на отклонённое действие** (шаг 13b): при finish по воздуху копающему
   отправляются `block_update` реального состояния и ack; при незагруженном
   чанке — только ack. Трейса с таким случаем нет; ваниль может отвечать иначе
   (например, `ack` без `block_update`). Проверяется записью трейса.
6. **`ACTION_ABORT = 0x02`** выведен поведенчески (пакет с прерыванием оставляет
   блок и получает ack с seq `00`), но байт `0x02` в S3 не встречается — только
   реконструкция по §1.4.
7. **Гипотезы о стадиях/времени (шаг 16a.2) — проверены по трейсам §1.7:**
   - `stage = floor(progress·10)` — **подтверждена**, но прогресс **не
     ограничен** единицей (10, 11, 13 — нормальное значение, не ошибка);
   - «стадии 0..9, финал `0xFF`» — **опровергнута**: диапазон шире, а `0xFF` —
     сброс, который приходит и при прерывании (без ломания блока);
   - «сервер шлёт обновление только при смене стадии» — **подтверждена**
     (у бревна пакеты каждые ≈6 тиков);
   - «прогресс += speed/hardness за тик» — **подтверждена** как
     `speed/hardness/30`: `reports/hardness.json` даёт листву 0.2, dirt 0.5,
     бревно 2.0, и `30·hardness` совпадает с 6/15/60 тиками; grass_block
     (0.6 → 18) даёт в старом счёте 16 — это сдвиг доставки первого пакета,
     а не скорость клиента (§1.8, оракул §1.7.1);
   - «сервер сам считает завершение» — **опровергнута**: после прогресса 1.0
     стадии продолжают идти, блок убирает клиентский `player_action 0x03`;
   - «клиент шлёт start (0x00) и finish (0x03)» — **подтверждена** (§1.2);
   - «2019/2020 идут только копающему» (комментарий `LevelEvent`) —
     **опровергнута** трейсом 1644: оба соединения получили 12×2019 и
     4×2020; 2001 — только наблюдателю (§1.9).
