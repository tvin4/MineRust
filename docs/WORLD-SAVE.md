# WORLD-SAVE.md — план сохранения мира на диск (Шаг 20c, только план)

Статус: **кода нет**, это проект следующего шага. Всё, что ниже, — предложение;
решения, помеченные «вопрос владельцу», принимает владелец (§8).

## 1. Что есть сейчас

- Мир читается из шаблона v3 (`E:\MineRust-data\worlds\minecraft-v3`,
  `.mca`-регионы): `world::region::load_region` → `StoredChunk` →
  `Chunk::from_stored` → `ReadyChunks` (`crates/world`). Шаблон **только
  читается**; `docs/BLOCK-BREAKING.md` стадия 7 запрещает писать в него.
- Изменения блоков живут **в памяти**: `net::store::ChunkStore` держит
  `Arc<ReadyChunks>` и по `set_block` пересобирает один чанк и публикует
  новый снимок. Кеш исчезает при перезапуске сервера.
- Источник изменений пока один — ломание блока (`player_action`), включая
  мгновенные блоки и каскады (`crates/net/src/game/block_action.rs`,
  `break_block.rs`). Установки блоков, жидкости, рост и мобы не меняют мир.
- Блок-сущности приходят из шаблона как готовый payload и не меняются;
  дропы/предметы и инвентарь не моделируются.
- playerdata уже пишет `save_dir/players/data/<uuid>.dat` с маркером
  `minerust-save.json` (version 1) и атомарной записью
  (`docs/PLAYERDATA.md` §11–§14). Мир пока не пишется никуда.

## 2. Цель и границы

Цель: после перезапуска сервера игроки видят тот же мир, который оставили —
как минимум все сломанные/поставленные блоки, позже блок-сущности и предметы.

Границы первого этапа (рекомендация):

- только блоки (state id) в загруженных чанках;
- шаблон v3 и `vanilla\world` не трогаются никогда (проверка как у
  playerdata: `ForbiddenPath` до bind);
- блок-сущности, дропы, инвентарь, свет, погода/время — вне этапа, но формат
  должен оставлять для них место;
- сервер без `save_dir` работает как сейчас (мир в памяти, `warn`).

## 3. Формат: три варианта

### A. Ванильный Anvil (`.mca`)

Писать `region/r.<x>.<z>.mca` в нашем `save_dir` полностью, как ваниль.

- **Плюсы:** мир можно открыть ванильным клиентом/сервером; формат уже
  читается нами; никакой привязки к шаблону.
- **Минусы:** нужно собрать полный NBT чанка — палитры секций, биомы,
  heightmaps, block entities, свет, `DataVersion`; ошибка в любом поле ломает
  чанк у клиента. Это большой объём и высокий риск, а движка света у нас нет.

### B. Наш формат: диффы поверх шаблона

Один файл на чанк: `save_dir/chunks/<x>.<z>.mrchunk` (плюс `world.json`).

- **Плюсы:** мало данных (только изменённые клетки), просто и быстро, легко
  сделать атомарным и проверяемым, не нужно трогать свет/биомы.
- **Минусы:** мир читается только нашим сервером и только вместе с тем же
  шаблоном; при смене шаблона диффы могут «повиснуть» (нужна проверка
  идентичности мира, §6).

### C. Гибрид (рекомендация)

Этап 1 — формат B. Позже, если владельцу нужен мир, открываемый в ванили,
отдельная команда/шаг «экспорт в Anvil» (A) поверх тех же данных.

Предлагаемая схема B:

```
save_dir/
  minerust-save.json          # маркер, version 2 (+ блок "world")
  players/data/<uuid>.dat     # как сейчас
  world.json                  # идентичность мира и шаблона
  chunks/<x>.<z>.mrchunk      # только изменённые чанки
```

`minerust-save.json` (version 2):

```json
{ "format": "minerust-save", "version": 2, "data_version": 5023 }
```

`world.json`:

```json
{
  "template": "E:/MineRust-data/worlds/minecraft-v3",
  "level_dat_sha256": "…",
  "data_version": 5023,
  "generator": "minerust-world-save/1"
}
```

`<x>.<z>.mrchunk` — маленький бинарный документ (не NBT, чтобы не тащить
gzip на каждую запись): magic `MRSV`, u8 version, i32 chunk x/z, u32 count,
затем `count` записей `(u16 cell index внутри чанка, VarInt state id)`,
u32 CRC32. Пустой список = чанк вернулся к шаблону (файл можно удалить).
Клетка кодируется индексом секции+позиции, а не мировыми координатами —
компактнее и не зависит от границ чанка.

Почему не «журнал изменений» (append-only log): журнал растёт без границ и
требует компакции. Файл-на-чанк перезаписывается целиком из текущего
состояния, поэтому компакция не нужна; размер ограничен числом изменённых
клеток.

## 4. Что, где и когда сохранять

- **Где:** `save_dir/chunks/` рядом с `players/`. Один `save_dir` на мир —
  маркер общий (§6). Другой каталог сохранений = другой мир (перенос вручную
  при остановленном сервере).
- **Что:** набор «грязных» чанков и для каждого — карта
  `(cell index → state id)` текущего состояния. Источник — `set_block`:
  в тике (поток игры) после успешной замены клетка добавляется в
  `DirtyChunks`; отдельного сканирования `ChunkStore` нет.
- **Когда:**
  - автосейв каждые `world_autosave_ticks` (предложение: тот же default
    6000, отдельная настройка, чтобы можно было развести с playerdata);
  - при остановке сервера (до `player saves flushed`, см. §6 про порядок);
  - позже — команда `/save` (когда появится чат/команды).
- **Как:** тик только снимает снимок грязных чанков (копия карт, очистка
  флага «грязный» не раньше успешной записи) и кладёт в очередь отдельного
  потока записи — по образцу `playerdata::Sink`. Тик не делает I/O и не берёт
  новых блокировок (AGENTS.md: никаких `Mutex` в горячем пути).
- **Ошибка записи:** `warn`, грязные чанки остаются в наборе и попадут в
  следующий автосейв; сервер продолжает работать.
- **Порог на один сейв:** не больше N чанков за проход (например 256), чтобы
  очередь не росла бесконечно; остаток — следующим тиком.

## 5. Загрузка

Порядок при старте:

1. прочитать шаблон (`load_region` по списку регионов) как сейчас;
2. открыть `save_dir`, проверить маркер и `world.json` (§6);
3. наложить диффы на `ReadyChunks` **до** `warm_world`/`bind`, чтобы первый
   вошедший игрок сразу видел изменения;
4. чанк без файла — шаблонный; битый файл/CRC/неизвестный state id —
   `warn` и шаблонный чанк, файл остаётся на диске для разбора;
5. дальше — обычный путь (`ChunkStore`, join, чанки).

Слияние идёт по чанкам целиком: дифф заменяет только перечисленные клетки,
остальное — из шаблона. Поэтому чужие/лишние клетки не «протекают».

## 6. Согласованность и идентичность мира

- **Идентичность.** `world.json` хранит SHA-256 `level.dat` шаблона и
  `DataVersion`. Несовпадение → `warn` и диффы **не применяются** (мир
  выглядит как шаблон), пока владелец не решит иначе настройкой
  `save_ignore_world_mismatch = true`. Это защищает от «диффы от другого
  мира» лучше, чем один маркер.
- **Атомарность.** Каждый файл: `.tmp` → `sync_all` → `rename`, затем
  `fsync` каталога на Unix (`playerdata` уже так делает). Windows —
  переименование журналируется NTFS, `fsync` каталога не нужен.
- **Порядок на остановке.** Сначала мир (снимок грязных чанков), затем
  игроки: последняя позиция игрока окажется в мире, который он видел.
  Обратный порядок может записать позицию в ещё не сохранённый мир — не
  смертельно, но менее честно.
- **Крах между сейвами.** Мир и playerdata стареют независимо; окно потерь
  мира = `world_autosave_ticks`. Игрок может оказаться в блоке, который
  «вернулся» после краха; сервер обязан не падать на такой позиции (сейчас
  коллизий нет, так что это безопасно).
- **Одновременная правка во время сейва.** Снимок берётся на границе тика;
  всё, что изменилось после, остаётся грязным и попадёт в следующий проход.
- **Удаление файла.** Чанк, вернувшийся к шаблону (все клетки совпали),
  пишется как пустой дифф и файл удаляется — иначе «мусор» копится.

## 7. Связи с другими подсистемами

- **playerdata:** общий `save_dir` и маркер (version 2). Существующие S13/S15
  обязаны остаться зелёными; тесты маркера обновить (version 1 → 2 с
  обратной совместимостью чтения).
- **Блок-сущности:** сейчас payload приходит из шаблона; дифф блоков его не
  трогает. Когда появятся сундуки/печи, дифф чанка должен нести и NBT
  блок-сущности (поле-расширение в формате, version bump). Известная
  проблема `trial_spawner: Registry does not exist` — отдельная задача
  configuration-фазы, не сохранения.
- **Предметы/дропы/инвентарь:** не моделируются. Их сохранение — этап 3:
  отдельный файл `entities/<x>.<z>.mrent` или расширение `.mrchunk`.
- **Свет:** движка нет, свет берётся из шаблона; дифф блоков свет не
  пересчитывает (как и сейчас в памяти). В `.mrchunk` свет не пишется.

## 8. Тесты и сценарий

Юнит-тесты (`world-save`/`world` крейт):

- round-trip диффа: кодирование/декодирование, отрицательные координаты,
  границы чанка (`x = -1`, `z = -1`), пустой дифф;
- CRC/битый файл → `None`/`warn`, шаблонный чанк;
- несовпадение `level_dat_sha256` → диффы не применяются;
- неизвестный state id → клетка пропускается, остальные применяются;
- атомарная запись: `.tmp` не остаётся, каталог синхронизируется (как в
  `playerdata`), ошибка записи не теряет грязный чанк;
- автосейв: после успешной записи набор пуст, повторный сейв не пишет файлов;
- тик не делает I/O: сейв только кладёт снимок в очередь (структурный тест
  по образцу `playerdata`).

Интеграционный тест (без клиента): маленький шаблон → `set_block` →
автосейв/остановка → новый `Store`/`ReadyChunks` → блок новый; SHA-256
шаблона не изменился.

Живой сценарий `s16-world-save` (`tools/testclient/scenarios/`):

1. чистый `save_dir`, ванильный шаблон, debug/release-сервер;
2. A ломает 3 блока в известных координатах (dirt, log, stone — разные
   hardness), B наблюдает;
3. ждём автосейв (`world_autosave_ticks` маленький, например 200);
4. останавливаем сервер штатно, запускаем снова с тем же `save_dir`;
5. A входит и `observe`/`block` подтверждает воздух в этих клетках; B видит
   то же; соседние клетки не изменились;
6. негативные прогоны: битый `.mrchunk` (шаблон + `warn`), чужой
   `world.json` (диффы не применены), шаблон и `vanilla\world` неизменны
   (SHA-256), `save_dir` без маркера — `warn` и работа.

Замер: сейв 1000 изменённых клеток в отдельном потоке, тиковое время снятия
снимка (цель — микросекунды, как `autosave queued` у playerdata).

## 9. Объём работы и риски

Разбивка (предложение, 4 шага):

| шаг | содержание | объём |
|---|---|---|
| 21a | формат `.mrchunk` + `world.json` + чтение/запись + юнит-тесты | ~300–400 строк, 1 шаг |
| 21b | `DirtyChunks` в тике, автосейв, остановка, поток записи | ~200–300 строк, 1 шаг |
| 21c | загрузка при старте, проверка идентичности, негативные тесты | ~150–250 строк, 0,5–1 шаг |
| 21d | живой `s16` + docs/PROGRESS/MECHANICS | ~1 шаг |
| 21e (опция) | экспорт в Anvil | отдельный этап, высокий риск |

Суммарно: средний объём, основной риск — не код, а **привязка к шаблону** и
ожидания совместимости.

Риски:

- **Шаблон изменится** (новая версия мира) → диффы не применить; лечится
  проверкой SHA-256 и понятным сообщением, но мир придётся начать заново.
- **Ванильная совместимость.** Формат B не читается ванилью; если владелец
  ждёт «открыть мир в обычном Minecraft», это отдельный этап A.
- **Размер.** Много изменённых чанков (взрывы, массовые каскады) → много
  файлов; порог на сейв и запись только грязных чанков держат это под
  контролем, но диск может расти.
- **Крах/питание.** Атомарность на файл есть; потерять можно только
  последние `world_autosave_ticks` изменений.
- **Свет/блок-сущности.** Пока не сохраняются и не пересчитываются —
  известное ограничение, не регрессия.

## 10. Вопросы владельцу (с рекомендацией)

1. **Формат:** свой дифф поверх шаблона (B), ванильный Anvil (A) или гибрид
   (C)?
   *Рекомендация: C — этап 1 = B, Anvil-экспорт отдельным шагом, если нужен.*
2. **Совместимость:** должен ли мир открываться ванильным клиентом/сервером?
   *Рекомендация: не в первом этапе; если да — сразу планировать A, это
   удорожает шаг в 2–3 раза.*
3. **Идентичность мира:** проверять SHA-256 `level.dat` и `DataVersion` и
   **не** применять диффы при несовпадении (с явной настройкой обхода)?
   *Рекомендация: да, отказ + `warn` по умолчанию.*
4. **Интервал автосейва мира:** 6000 тиков (как playerdata), отдельная
   настройка, или сейв только на остановке?
   *Рекомендация: отдельная `world_autosave_ticks = 6000`; сейв только на
   остановке — слишком большой риск потерь.*
5. **Порог сейва:** ограничивать число чанков за проход (256)?
   *Рекомендация: да, остаток — следующим тиком.*
6. **Что в этапе 1:** только блоки, блок-сущности/предметы — позже?
   *Рекомендация: только блоки; формат оставляет поля под расширения.*
7. **Где хранить:** общий `save_dir` с playerdata (один маркер) или
   отдельный `world_save_dir`?
   *Рекомендация: общий `save_dir`, один мир — один каталог.*
