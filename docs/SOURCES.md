# SOURCES.md — аудит источников данных (M1–M2, по состоянию на пред-M3)

Правило источников — в `AGENTS.md` («Источники истины (порядок)»):

1. данные из jar/генератора игры;
2. сравнение с ванильным сервером через parity-тесты;
3. вики только как подсказка.

Любая механика без проверки по (1) или (2) считается непроверенной и
помечается в коде `// SOURCE: wiki, unverified`.

Статусы, использованные ниже:

- **авто (отчёт)** — сверено с `reports/packets.json` генератора данных из
  вашего клиентского jar (см. «Как проверить»);
- **авто (fixture)** — проверено самодельными фикстурами в тестах;
- **jar** — данные читаются из реального клиентского jar, а не лежат в
  репозитории (ignored-тест по `MINECRAFT_JAR`);
- **живой клиент** — проверено в игре 26.3 настоящим клиентом;
- **не проверено** — задокументировано/угадано, помечено
  `// SOURCE: wiki, unverified`.

> Аудит честный: **раздел «живой клиент» пуст**. Smoke-тест показывал, что
> сервер поднимается, но ручная проверка в игре по M1/M2 осталась за
> владельцем (`docs/PROGRESS.md`). Теперь к авто (отчёту) и fixture-тестам
> добавился шаг (2) порядка источников: крейт `parity` со срезами status и
> join (см. «План» внизу — каркас сделан, срезы идут в части 2). Главная
> ценность этапа: все ID-константы пакетов сверены с генератором игры, а
> payload'ы status/login сверены с трейсом настоящего ваниля.

## Что было непроверяемо раньше и стало проверяемым

Генератор данных игры (`net.minecraft.data.Main --reports`) даёт полный
список пакетов: состояние → направление → имя → `protocol_id`. Отчёт
**не коммитится** (как и реестры — это ваша копия игры), путь задаётся в
`server.toml` полем `packets_report`. При старте: отчёт загружается →
`verify()` сверяет все ключи сервера → расхождение = fail-fast ошибка. Без
поля в конфиге сервер работает на встроенных дефолтах и пишет warn.

Аналогично генератор даёт `reports/registries.json` (реестр → запись →
`protocol_id`), путь — поле `registries_report` в `server.toml`. Из него
берутся числовые id статических реестров (block, item, potion, …) для
Update Tags, а состав тегов проверяется парити-тестом
`update_tags_parity` против трейса реального сервера (состав 15 реестров и
значения 773 тегов совпадают; порядок — итерация внутренних мапов ванили,
`docs/PROGRESS.md`, раздел «Известные проблемы»). Пустые теги (dialog)
отправляются как есть — поведение подтверждено трейсом ванили.

Состав Registry Data проверяется парити-тестом `registry_data_parity`
против того же трейса: **32 реестра и 432 записи — имена реестров, ключи
записей, их количество и порядок совпадают с ванилью полностью**
(26.3; до фикса было 29 реестров — три ванильских реестра
`block_transformer`, `decorated_pot_pattern`, `worldgen/block_state_provider`
виноваты в живой ошибке клиента «Missing element»). Содержимое всех
реестров читается из клиентского jar (`data/minecraft/<реестр>/`), трейс —
только эталон; отчёт `registries.json` этих трёх реестров не содержит.

## Как проверить (команды)

Отчёты генератора живут вне репозитория — в `C:\MineRust-data\reports\`
(`server.toml` указывает на них полями `packets_report`/`registries_report`;
и `server.toml`, и `C:\MineRust-data` в Git не попадают: первый в
`.gitignore`, второй лежит вне репозитория).

```powershell
# 1. Сгенерировать отчёты из вашего клиентского jar (не коммитятся):
tools\generate-reports.ps1 -VersionJson "...\meta\<uid>\<version>.json" -Output "C:\MineRust-data"
#    → C:\MineRust-data\reports\{packets,registries}.json

# 2. Сверить наши ID констант с отчётом (test игнорируется без env):
$env:MINECRAFT_PACKETS_REPORT = "C:\MineRust-data\reports\packets.json"
cargo test -p data compiled_packet_ids_match_the_real_report -- --ignored

# 3. Прогнать все тесты с реальным jar и/или отчётом:
$env:MINECRAFT_JAR = "...\client.jar"
cargo test --workspace -- --ignored

# 4. Указать отчёт серверу (сервер при старте сверит его с ключами):
#    server.toml: packets_report = "<...>/reports/packets.json"
```

## Пункты статуса

- **ID пакетов**: проверены автоматически — 100% совпадений с 26.3 —
  закрывает то, что раньше было «вики без проверки».
- **Реестры/теги/NBT-данные**: источник = jar, авто + ignored-тест.
  Registry Data — **проверено parity** (32 реестра / 432 записи = ванили);
  Update Tags — состав и id = ванили, порядок наш (`docs/DECISIONS.md`).
- **Срез 1 (part 2)**: **проверено parity** — status_response (payload
  = ваниль байт-в-байт), структура login_finished + случайный session uuid,
  раскладка полей login (play) и формула hashed_seed, маска/раскладка
  player_info_update (encode = записанные байты), интервал keep-alive 15 с.
  Всё это больше не «вики без проверки».
- **Осталось вики-без проверки**: таймауты (30 с до play, 30 с на
  keep-alive), семантика восьмого действия player_info, поведение клиента
  без Known Packs. Состав join-последовательности (вензель, чанки) —
  расхождения остаются в отчёте до части 3.
- **Живой клиент**: ни одного подтверждения этой части — ручная проверка
  (вход + статус-лист) висит на владельце.

## План: крейт `parity` (шаг (2) порядка источников)

Идея: **наш сервер и настоящий ванильный `server.jar` общаются с одним и тем
же клиентским скриптом, результаты сравниваются попиксельно.**

1. **Запуск ванили.** Владелец разово кладёт официальный `server.jar` с
   minecraft.net для 26.3 в директорию (в репозиторий не идёт) и однажды
   принимает EULA (`eula=true` — нашему репозиторию не касается). Тест читает
   путь из `MINECRAFT_VANILLA_SERVER_JAR`, поднимает `java -Xmx1G -jar
   server.jar --nogui` в temp-world (auto-generated flat, online-mode=false,
   закрытый код порта), ждёт строки `Done`, гасит в конце.
2. **Общий обмен пакетами.** Один и тот же тест-клиент открывает TCP к
   ванили и к нашему серверу, прогоняет одинаковые сценарии (SLP → ping,
   offline-логин → configuration → play), пишет пакетный трейс
  `(state, direction, name, id, payload-поля)` в JSON.
3. **Сравнение.** Diff двух трейсов (и `protocol_id` из обоих источников) со
   стабилизацией случайностей (имя игрока, UUID, случайные id) — отчёт в
   `target/parity-report.json`. Любое отличие = провал теста.
4. **Срезы этапами:** (1) status SLP, (2) login+configuration (последовательность
   и состав Registry Data/Update Tags), (3) play: join-последовательность и
   все коды полей. Срез (2)/(3) пересекается с M3 (чанки): compare Chunk Data
   станет первым чекпоинтом M3.

**Предложение по сроку:** сделать **первым шагом внутри M3**, а не до M3:
(а) ванильный сервер стартует только на вашей машине с уже принятым EULA, и
польза от сравнения появится, как только у M3 появится что сравнивать
(чанки); (б) M2 уже закрыт автотестами (все 31 ключ сверены с отчётом,
реестры/теги — из jar); (в) отдельный пре-этап «до M3» отложил бы M3 и дал
бы мало нового — status/login-трейсы без чанков уже покрыты fixture-тестами.
Первый шаг M3 = каркас `crates/parity` (срезы 1→2), срез 3 — сразу при
появлении первых чанков.
