### Таймлайн S8 и правило для шага 14d

Порядок записей B для entity 76 устанавливает следующую последовательность
(время приблизительное, по часам B; состояние подтверждено байтами metadata):

1. На сухой земле спринт: flags `0x08`, без записи pose 3.
2. После телепорта в воду, **ещё в покое и до нажатия спринта**: pose 3
   (`SWIMMING`), flags `0x00` в первом переходе. Значит pose плавания
   определяется нахождением в воде, но первый покойный flags-сэмпл не содержит
   бита `0x10`.
3. Начало спринта в воде: flags `0x18` (`SWIMMING | SPRINTING`), pose остаётся 3.
4. Отпускание спринта, пока игрок всё ещё в воде: flags `0x10`, pose остаётся 3.
   Это подтверждает, что после перехода sprint-off ваниль оставляет бит
   `SWIMMING` установленным.
5. Выход из воды: flags `0x00` и pose возвращается к 0 (standing).

Для 14d реализуется детерминированное правило переходов: `swimming = игрок
находится в water state у ног`; pose = 3 при swimming и 0 вне воды; flags
вычисляются как sneak `0x02` | sprint `0x08` | swimming `0x10`. Поэтому наша
модель в первом покойном состоянии в воде выдаст flags `0x10`, тогда как
первый S8 water-idle sample был `0x00`; позже в том же S8, после sprint-off,
`0x10` подтверждён. Это явное расхождение реализации с начальным образцом, не
основание подменять состояние ради одного переходного кадра. Таймер воздуха,
подводность глаз, скорость/атрибуты и звуковые эффекты этим правилом не
реализуются.

## 2. Как сервер узнаёт, что игрок в воде (b) — реализация шага 14d

Игровой поток читает block state из общего `ChunkStore` и проверяет water у
ног: `floor(x), floor(y), floor(z)` — блок, в котором начинается
ограничивающий объём игрока. Выбор «у ног» — приближение; S8 подтверждает
позу плавания в воде, но не определяет точный вертикальный sample.
Глаза/полное погружение пока не различаются. Live-прогон 14d показал, что
`floor(y − 0.1)` ошибочно берёт блок *под* ногами, когда пловец стоит на дне:
вода у ног, но снизу твёрдый блок, и swimming ложно становится `false`.
`floor(y)` в воде даёт воду, на суше — воздух.

- `Region` продолжает владеть игроками, scheduler получает общий
  `Arc<ChunkStore>` и перед visibility pass обновляет swimming. Block state id
  классифицируется по загруженному `reports/blocks.json`; только
  `minecraft:water` считается водой (не lava и не waterlogged block).
- Отсутствующий chunk/section считается «не вода», без ошибки и без блокировки
  тика. В неготовой области переход в swimming не появится, пока block lookup
  недоступен.
- **Стоимость.** Точных замеров нет (бенчмарка загрузки чанка/света нет —
  «не найдено»). Есть ориентиры: сборка батча ≈ 2.4 с
  (`crates/server/src/template.rs`), вход ≈ 109 мс/бота при стриме
  3348 чанков (`docs/BENCH-M4.md`), кеш входа снижал 6058–7747 мс → 3015–3022 мс
  (`docs/PROGRESS.md`). Кеш `ReadyChunks` уже индексирован O(1) по чанку
  (`crates/net/src/chunks.rs`), поэтому добавление «hot path: блок по позиции»
  — это в первую очередь вопрос хранения секций в читаемой форме, а не скорости
  сети.
- **Что мерить перед реализацией:** стоимость `get_block` на горячем пути
  (тик) и цену построения `ChunkStore` из шаблона один раз при старте.

## 3. Сценарии проверки (c)

**Автоматический сценарий готов**: `tools/testclient/scenarios/s8-water.json`
(шаг 13c) — A спринтует по земле 3 с, RCON `/tp` в столб воды (106.5, 41, −30.5),
спринт-заплыв 3 с, обратный `/tp` на старт; B наблюдает, трейсы обеих сторон
сохраняются, чеки в `summary.json`. Правка шаблона не нужна — телепорт делает
только RCON ванильного стенда; на `-Target ours` сценарий честно фиксирует
«нет RCON» и остаётся vanilla-trace фактом.

Исторические варианты из плана (справочно):

1. **Dev-параметр стартовой позиции** в конфиге сервера (`spawn_override =
   (x,y,z)`) — тогда клиент входит сразу в воду. Требует правки сервера.
2. **Правка копии мира, а не шаблона:** `Prepare-RunWorld` уже копирует v3 в
   рабочий мир прогона; можно изменить `SpawnX/SpawnY/SpawnZ` в
   `<run>\world\level.dat` (копия), оставив v3 нетронутым. Нужен tiny-tool
   записи NBT (кодек в `crates/protocol` уже есть).
3. **Телепорт через сущность**: у нашего сервера нет команд/RCON, поэтому
   «игрок сам идёт в воду» (вход пешком/падение) — самый ручной, но честный путь.
4. Координаты воды известны из `docs/RUNBOOK-STEP8-TRACES.md`: столб у
   (105..107, −28..−32), вода y=37..41, точка (106.5, 41, −30.5) используется
   сценарием S8, чанк (6,−2) — тот же, что спавн, значит входит в готовое
   окно R=10 (473 чанка).

**Риски:** клиент может утонуть/получить эффект, если стоять долго; вода в
шаблоне может быть «мелкой» для позы плавания (глубина до 5 блоков);
автоматический стенд сейчас не может навести прицел куда надо (S6 красный по
причине стенда), поэтому движение в воде лучше проверять ручным клиентом
(`tools\testclient\client.bat`) с записью mcproxy.

2. **Разбор трейса** скриптом (`tools/trace-analyze/…`) и фиксация: значения
   flags/pose при плавании, есть ли `water_movement_efficiency`, serverbound

   `docs/MECHANICS.md` (п. 12) и в отдельную заметку фактов.
3. **Юнит-тесты побайтно** на encoder'ы, которые понадобятся (metadata flags/pose
   при плавании, атрибуты) — по hex из нового трейса, до серверной логики.
4. **Серверная механика:** общий `ChunkStore` (раздел 2) → определение «в воде»

5. **Live-проверка:** два клиента, A входит в воду и плывёт, B видит позу

**Относительный размер:** по механике переходов плавание ≈ B (присед/спринт)
плюс новое чтение блоков; полное плавание (всплески/звук/частицы) — как стадии
3–4 ломания. Первый шаг (запись трейса) — маленький по коду, но блокирующий.
