# DECISIONS.md — осознанные решения и осознанные отличия от ванили

Каждая запись: что решили, почему, и чем это проверяется. Отличия от
поведения ванильного сервера, которые мы **не** собираемся воспроизводить,
тоже здесь — чтобы никто не принял их за недоделку.

## Порядок реестров и тегов в Update Tags оставляем наш

**Решение.** Пакет `minecraft:update_tags` отправляем в детерминированном
порядке: реестры — по алфавиту идентификатора, теги внутри реестра — так
же по алфавиту; идиентификаторы записей внутри тега совпадают с ванилью
побайтово по значениям (состав и id).

**Почему не повторяем ваниль.** Ванильный сервер итерирует внутренние
Java-мапы: порядок реестров в пакете и тегов внутри реестра в трейсе
фиксирован для одного запуска и выводимого из данных правила не даёт.
Клиенту порядок не важен — пакет несёт имена вместе с id, на живом
прогоне клиент к порядку претензий не предъявлял.

**Проверка.** Ignored-тест `crates/parity/tests/update_tags_parity.rs`
сравнивает состав (15 реестров, 773 тега) и id; при совпадении порядка
он дополнительно сравнивает payload байт в байт, при расхождении порядка —
предупреждает, но считает содержимое сошедшимся.

## Порядок реестров в Registry Data — наш детерминированный

**Решение.** Реестры в `registry_data` уходят в алфавитном порядке
идентификатора (`BTreeMap`), порядок **записей внутри** реестра —
алфавитный по ключу, что для всех 32 реестров 26.3 совпадает с порядком
ванили (сверено `crates/parity/tests/registry_data_parity.rs`).

**Проверка.** Тот же тест: 32 реестра, 432 записи, множества ключей и
порядок сравнены с трейсом ванильного сервера.

## Known Packs не реализуем: реестры уходят целиком

**Решение.** Handshake `minecraft:select_known_packs` (configuration,
в обе стороны) мы не реализуем: сервер отправляет все данные реестров
полными пакетами, как и сегодня.

**Почему не повторяем ваниль.** Ваниль использует этот обмен, чтобы
клиент с уже известными ему данными (ванильные датапаки) принял их «по
хешу» и сервер мог пропустить часть отправки. Реализация требует
сверять версии/хеши пакетов с реальными данными из jar пользователя, а
полная отправка без обмена — допустимый и более простой протокольный
путь: клиент данные принимает (живая проверка — отдельно, см.
`docs/PROGRESS.md`). Формально это расхождение состава пакетов остаётся
видимым в `target/parity-report/join-diff.md`, и мы это принимаем.

**Проверка.** Таблица `join-diff.md`: строки `select_known_packs` (1
вверх, 1 вниз у ванили, 0 у нас). Реестры сверены отдельно —
`crates/parity/tests/registry_data_parity.rs`.

## Сжатие трафика отложено

**Решение.** Пакеты не сжимаем. Порог ванильного сервера для прогонов
парити выставлен `network-compression-threshold=-1` (отключено), так
что записанные трейсы и живые подключения идут без сжатия.

**Почему не повторяем ваниль.** Своя реализация (_VARINT-длина +
zlib-фреймы, порог в protocol version, согласование в configuration)
добавляет поверхность для ошибок прямо на сравниваемом пути; при
отключённом сжатии у ванили она и не задействована. Включать — после
того, как join-парити станет стабильным.

**Проверка.** `server.properties` парити-гарнесса (порог `-1`);
состояние пересматривается при задаче «сжатие» в `docs/PROGRESS.md`.

## Присылаем только готовые чанки, свет берём из NBT; `light_update` отложен

**Решение.** Чанк уходит клиенту, только если он удовлетворяет правилу
**ChunkReady**, выведенному из данных (не из догадок — `crates/parity`:
`world_inspect`, шаг 3.0):

- `DataVersion` чанка совпадает с версией мира, иначе — явная ошибка
  `UnsupportedDataVersion` (чанк другой версии формат не угадываем);
- корневой `Status` ∈ {`minecraft:full`, `minecraft:initialize_light`};
- внутри `sections` есть хотя бы один массив `BlockLight`/`SkyLight`.

Чанки вне правила **не отправляем вообще**: не подменяем пустыми и не
досчитываем `Status`. Запрос такого чанка возвращается как явный результат
`ChunkNotReady { status }`, а список недостающих пишется в
`docs/PROGRESS.md` как «ждёт генерации (M6)».

Свет **не считаем** — отправляем только то, что лежит в `BlockLight` и
`SkyLight` NBT секций. Пакет `minecraft:light_update` в первой порции не
реализуем: в трейсе ванили он начинается только после активности мира
(с #141, не в первом батче) и перестраивает свет по мере симуляции.

**Почему такое правило.** В шаблоне мира (529 чанков) под правило
подпадают ровно 9 чанков — те самые, которые ваниль реально отправила
при джоине (совпадение трёх множеств: отправленные = Status потолка =
имеющие свет; сверяется в `world_inspect`). Остальные 520 лежат в ранних
стадиях генерации.

**Проверка.** `world_inspect` ведомостью показывает `Status`/свет по
каждому чанку и список в Rule; parity-срез первой порции (шаг 3.4)
сравнивает сырые байты payload только для чанков под правилом.

## Шаблон мира изменён: `minecraft:respawn_radius = 0`

**Решение.** В `C:\MineRust-data\world-template\data\minecraft\game_rules.dat`
правило `minecraft:respawn_radius` записано как `0` (исходное значение `10`).

**Почему.** Без фиксации радиус позиция игрока при каждом входе и центр
`set_chunk_cache_center` плавали между прогонами (замерено: `(89.5,131,−24.5)`
и `(91.5,140,−32.5)` при одном и том же `set_default_spawn_position` из
level.dat), а парити-срез сравнивает первые чанки и центры — нестабильная
стартовая точка делает сравнение нечестным. С `0` вход стабилен 2/2:
`(96.5,145,−31.5)` = блок спавна из level.dat `[96,145,−32]`, центр `(6,−2)`,
состав первых 9 чанков и их порядок байт-в-байт повторяются.

**Запас.** Исходный `game_rules.dat` (со значением `10`) сохранён рядом с
данными игры: `C:\MineRust-data\game_rules.dat.orig` — восстановление это
копия файла обратно в `world-template/data/minecraft/`.

**Проверка.** Два прогона `join_slice` до/после: см. `docs/PROGRESS.md`
(раздел шага 3.0); sha256 шаблона до/после — менялся только этот файл.

## Парити-критерий чанков (шаг 3а): сырые байты, кроме световых массивов

**Решение.** Критерий «наш payload == payload ванили» для `level_chunk_with_light`
формулируем так: сырые байты совпадают **полностью, кроме содержимого
световых массивов** (массивы `sky`/`block` внутри BitSets длиной 2048 Б
каждый). Свет сравниваем по структуре: маска секций, число и длины
массивов, отсутствие пересечений с empty-масками, точный конец payload.
Расхождения света печатаются отдельным отчётом и **не валят тест**.

**Почему.** Уже подтверждено (шаг 3.2, `light_arrays_*`): содержимое
световых массивов в NBT шаблонного мира и на wire у ванили разное —
факт зафиксирован как известное расхождение. Гнаться за побайтовым
совпадением света можно только с работающим движком освещения, а это
отдельный этап; сравнивать же несравнимое байт-в-байт значило бы
постоянно иметь красный тест без возможности отделить регрессию в
палитрах/биомах от старого расхождения света.

**Проверка.** Срез `chunk_slice` (шаг 3.3f) генерирует таблицу
`target/parity-report/chunk-diff.md`: световые поля в ней отдельными
строками (4 маски + 2 группы массивов), свет расходится у всех 9 чанков
и это не валит тест. Дополнительно кодеки закреплены тестом
`encode(decode(...)) == байты` (`chunk_codec.rs`; сравнение байт
игнорирует световые массивы, структура — нет).

## Секция без света в NBT: отправляем sky 15 / block 0 (временное)

**Решение.** Если чанк проходит правило ChunkReady, но отдельная секция
в `sections` не содержит массивов `SkyLight`/`BlockLight`, в wire-записи
секции отправляем `SkyLight = 15` (полностью освещено небом),
`BlockLight = 0`. Помечено в коде и в `docs/SOURCES.md` как временное
решение.

**Почему не parity.** Это не копирование ванильного значения, а
нейтральный дефолт, чтобы клиент не получил «нет данных света» на
секции. Соответствие ванилю не проверено — поэтому это осознанный
откат от парити, а не утверждение о поведении ванили.

**Проверка.** Тесты фрейминга (`light_framing.rs`) и попиксельного
поиска (`payload_map.rs`) фиксируют, какие секции реально имеют свет в
данных. Замер по шаблонному чанку (6,−2) (`target/parity/payload-map.txt`):
сохранены всего 5 световых массивов из 24 секций — `BlockLight` Y −3 и
Y −2, `SkyLight` Y 8, 9, 10; у остальных 19 секций сохранённого света
нет вообще. Правило §141 применяется уже сейчас, и видно оно на проводе:
в таблице `chunk-diff` (тот же чанк) у ванили 3 sky-массива, у нас 24
(21 синтезированы), sky-маска ванили `[13, 14, 15]` против наших 24 бит.
Это осознанное известное расхождение до движка освещения — по остальным
8 чанкам состав сохранённого света отдельно не замерялся.

## Чанки шаблона в `initialize_light`: расхождения блоков и block entities — догенерация ванили, не наша отправка

**Решение.** Расхождения «блоки / non-air / block entities / свет» между
нашей записью джоина и записью ванили (**жизни** 07.11, `join-vanilla*.json`)
признаём следствием состояния шаблона мира, а не дефектом нашего кода
отправки. Наш сервер отправляет чанк ровно как он лежит в шаблоне — и в
этом **прав**: в шаблоне (7,−2) ровно 0 записей `block_entities`, и мы
отправляем 0.

**Причина (данные, не догадка).** Статусы шаблонных спавн-чанков:

| чанк | Status в шаблоне | Status в мире, сохранённом ванилью | клеток отличаются wire↔шаблон |
|------|------------------|------------------------------------|-------------------------------|
| (6,−2) | `full` | `full` | **0** |
| остальные 8 | `initialize_light` | `full` | 808…1567 |

Ванильный сервер, загружая чанк со статусом ниже `full`, доводит его
генерацию до конца: блоки перезаписываются (частые переходы шаблон→провод:
`stone→clay`, `stone→andesite`, `deepslate→sculk`), статус становится
`full`, а в (7,−2) проставляются ровно те 2 `sculk_sensor`
`(121,−40,−23)` и `(124,−40,−20)`, которых в шаблоне нет (на этих
координатах шаблон держит `sculk_vein`/`air`). Полное совпадение по чанку
(6,−2) (единственный `full`) при 100% расхождении остальных восьми —
подтверждение по всем 9 чанкам.

**Почему не повторяем прямо сейчас.** Лечить надо шаблон (довести чанки
до `full` прогоном ванили), а не формат отправки: наш формат байт-в-байт
уже совпадает с записью ванили для чанков в `full` (`runs_recon`:
wire↔сохранённый мир — 0..16 клеток разницы на чанк, остаток — поздние
правки мира после записи). Решение о перегенерации шаблона за владельцем.

**Проверка.** Ignored-тест `crates/parity/tests/runs_recon.rs`
(`cells_of_the_recording_the_template_and_the_saved_world`): 9 чанков ×
24 секции × 4096 клеток, сравнение имён блоков (не сырых слов — палитры
независимы) по трём сторонам: провод, шаблон, сохранённый ванилью мир.
Независимо результат подтверждён python-чтением NBT (список идентичен).

## Карты высот: ваниль пересчитывает их при загрузке — расхождение осознанное

**Решение.** Расхождения `heightmap` между архивными прогонами ванили
(`run3` против `join-vanilla`/`run4`) и между записью ванили и шаблоном
признаём **ожидаемым**: ваниль пересчитывает карты высот при загрузке и
сохранении чанков (в т.ч. в ходе той же доводки генерации до `full`).

**Данные.** Прогон `run3` отличается от `join-vanilla` **только** полями
мэп высот: секции (блоки/палитры), `block_entities` и свет совпадают
байт-в-байт. По матрице chunk-diff карты высот расходятся в 4 чанках из 9
(при этом биомы сходятся 9/9).

**Почему не повторяем.** Пересчёт высот — внутренняя деталь ванили на
стороне загрузки; сравнивать сырые массивы мэп между независимыми загрузками
невозможно, а догонять их значило бы считать карты высоты в нашем коде,
чего задача (шаг 3.3) не требует. В отчёте `chunk-diff.md` строка
heightmaps остаётся фактом расхождения.

**Проверка.** Тот же `runs_recon` (секции/BE/свет равны в run3↔join) и
матрица `chunk-diff.md` (строка «карты высот»).

**Правило радиуса отправки закодировано (п.6).**

(configuration → play, последний `client_information`),
`send_radius() = clamp(0, VIEW_DISTANCE)`, `write_chunk_batch(..., radius)`
с `retain` и info-счётчиком скипнутых; `VIEW_DISTANCE = 10` теперь
«серверный максимум», а не радиус по умолчанию. Тесты: `send_radius_tests`
и `chunks_outside_the_send_radius_are_not_sent`.

## Часть A2, п.5: остатки chunk-diff объяснены по данным (п.5 выполнен)

Правило жидкости в заголовке секции исправлено, порядки id карт высот и
block entities объяснены и зафиксированы как ожидаемые. Доказательства —
`test(parity): a2_findings` и отчёт `target/parity-report/a2-evidence.md`;
строка `section non-air/fluid` в `chunk-diff.md` после фикса — **9 из 9**

**Счётчик жидкости (`fix(world): count waterlogged and aquatic cells`).**
Из первых ячеек же ванили посчитаны все кандидаты правил против первых

## Часть A2, п.5: пейсинг батча — правило из трейса ванили, guard 1 с — наш

**Решение (коммит `6d113a8`).** Батч джоина пишется по одной порции за
оборот `select!` ветки play-цикла, а не целиком внутри ветки загрузки:
первая порция — **9 чанков** (`FIRST_FLUSH`), дальше ожидание ответа
`chunk_batch_received`, по ответу — немедленная следующая порция, затем
по одному тику (**50 мс**) и размером `ceil(chunks_per_tick)`.

**Данные (не догадка).** Трейс `target/parity/chunk-batch-vanilla.json`
(ваниль, 17377 пакетов): 72 чанка, 11 порций
`[9, 8, 8, 3, 8, 8, 2, 6, 8, 4, 8]`; ровно **один** серверbound
`chunk_batch_received` (payload `8.0`) сразу после `finished` первой
порции — дальше ваниль слал 10 порций без единого нового ack. После ack
ни одна порция не превышает 8 (=`ceil 8.0`); первая порция до ack = 9
(3×3 вокруг центра). Живой клиент до п.5 отвечал после всего батча
(`sub_batches=1`), потому что батч писался в одной ветке.

**Что наше, не протокол.** `PACE_WAIT = 1 с` — внутренний guard: тихий
клиент (скрипт-бот, который ack не шлёт) иначе получил бы хвост только
через бесконечное ожидание. После guard хвост уходит одной порцией —
старое поведение ботов сохранено.

**Проверка.** Юнит-тест
`net::connection::play::tests::the_first_flush_is_nine_then_the_vanilla_paced_tail`
проигрывает эту последовательность на реальном `play_state`:
`[9, 8, 3]` за ack 8.0, последняя порция ≥ 50 мс после предыдущей.

## M4: позиция игрока принимается без проверок; до TeleportAck позиции игнорируются

**Решение.** В M4 позиция игрока принимается тиком как есть, без
проверок движения — известная дыра (ваниль позицию клиента валидирует,

**Проверка.** `docs/ARCH-M4.md` §0 и шаг M4.2: живая проверка позиции

## Слот последней позиции — единственный осознанный `Mutex` M4.1

**Решение.** Слот «последняя позиция игрока» (`net::game::MoveSlot`)
хранится как `Mutex<Option<MoveState>>`. Это единственная блокировка
M4.1 в пути тика; всё остальное межпоточное — каналы или атомики
(метрики, `KickFlag`).

**Почему.** Позицию пишет задача соединения (по пакету) и читает тик:
это второй, после каналов, вид связи «последнее значение, старое
перезаписывается», а очередь тут неверна — очередь копила бы позиции, а
тику нужна только последняя. Варианты без блокировки (`AtomicU64` на
позицию, lock-free-слот) усложняют код M4.1 без выигрыша: критическая
секция — одна запись/чтение мелкой структуры, лок всегда свободен
(один писатель, один читатель), а `Move` уже помечен `[гипотеза]` в
`docs/ARCH-M4.md` §0. Тик никогда не ждёт: `take` берёт текущее значение
и уходит. Разбор и применение позиции — M4.2, там же возможен пересмотр
представления.

**M4.2.** Представление слота пересмотрено: вместо `packet_id` хранится
`MoveKind` (классифицирует соединение по runtime-id), payload остаётся
сырым, а разбор (`MoveState::decode`) и применение — в тике. `Mutex`-слот
не изменился, второй вид связи не появился.

**Проверка.** Юнит-тест `game::tests::the_move_slot_keeps_only_the_newest_packet`
(старое значение перезаписывается, `take` опустошает слот);
`docs/ARCH-M4.md` §0 (слот вместо сообщения).

## Байт флагов движения: бит 0 — on_ground, бит 1 не установлен (M4.2)

**Решение.** Последний байт пакетов движения (`move_player_pos`,
`move_player_pos_rot`, `move_player_rot`, `move_player_status_only`)
читается как **набор флагов**, а не `bool`. Бит 0 (`0x01`) — `on_ground`;
байт хранится сырым (`MoveUpdate::flags`, `PlayerPos::flags`) и пишется в
реплей полем `flags`. Любое значение `0x00..0x03` принимается (пакет **не**
отбрасывается).

**Данные.** Трейс живого клиента `target/parity/live-session.json` (26.3),
последний байт: `move_player_pos` — `0x00` (50), `0x01` (492), `0x02` (17),
`0x03` (35); `move_player_pos_rot` — `0x00` (101), `0x01` (467), `0x02` (18),
`0x03` (46); `move_player_rot` — `0x01` (387), `0x03` (5);
`move_player_status_only` — `0x01` (1). Значение бита 1 (`0x02`) по этим
данным **не установлено**: семантики в трейсе нет, поэтому в коде он не
именуется и не проверяется.

**Почему.** До фикса `read_bool` (`byte != 0`) `0x02`/`0x03` **не** отвергал,
но схлопывал бит 0: `0x02` давало `on_ground = true`, что неверно. Чтение
сырого байта сохраняет поведение клиента и не теряет данные.

**Проверка.** Тест
`movement::tests::every_flag_of_pos_and_pos_rot_decodes_with_bit_zero_as_on_ground`
(`0x00..=0x03` для pos/pos_rot); `game::tests::a_rotation_packet_keeps_the_position`
(флаг `0x02`: позиция стоит, `on_ground = false`).

**Дополнение (живая проверка владельца 10.11.2026).** 499 move'ов, из них
`flags=2` — 120 и `flags=3` — 66, наблюдались при упоре в стену и прыжке.
Это **только корреляция**: связь бита 1 с упором/прыжком по одним
наблюдениям не доказана; бит 1 по-прежнему не именуется, его значение
**не установлено**. Код не менялся.

## Окно чанков M4.4 A: форма из трейса включена только при R=10 (остальное — гипотеза)

**Решение.** `net::chunks::window(center, R)` — чистая функция: при `R=10`
квадрат полуширины `R+1 = 11` со срезанными по кругу `dx²+dz² ≤ 162` углами
(**473** чанка, форма из трейса ЧАСТЬ 0 и раунда 5), при любом другом `R` —
полный квадрат `(2R+1)²` (как и было). Порядок обхода детерминирован:
возрастание `dx²+dz²`, при равенстве — `(x, z)`; вторичный ключ по трейсу не
установлен, поэтому оставлен прежний.

**Почему только R=10.** ЧАСТЬ 0 измерила форму при R=6/8/10/12 (свежая копия
v2, бот стоит): все четыре — квадрат `R+1` со срезом `dx²+dz² ≤ K`, но `K` =
74/113/162/208 не ложится на простую формулу `K(R)`. Выводить её на другие R —
домысел, поэтому включён ровно измеренный контроль R=10; для остальных R форма
остаётся квадратом и помечена **«гипотеза, не проверено по трейсу»** (ваниль
на R=8 шлёт 329, мы — 289). Обновление формы при других R — отдельная задача
после формулы/трейсов.

**Индекс.** Ready-батч (`server::TemplateWorld::ready`) теперь несёт
`ReadyChunks`: wire-payload'ы и `(x, z) → позиция` (HashMap, построен один раз
при сборке батча на прогреве, O(1), без блокировок). Соединение строит окно по
центру кэша и радиусу, резолвит каждую координату через индекс и пропускает
координаты вне батча (край мира — не дыра). Одна строка `info`:
`in_window / sent / not_cached`.

**Проверка.** Юнит-тесты `net::chunks` (473, ряды 0..6→23,7→21,8→19,9→19,10→15,
11→13; симметрия; сдвиги 23/23/37; квадрат для R≠10; порядок; индекс);
парити-тест `chunk_slice::the_ready_index_resolves_every_template_chunk`
(729/729 на v2). `ARCH-M4.md` §4 (таблица ЧАСТИ 0), §6.

**ЧАСТЬ 2 — проверено на нашем сервере (10.11.2026).** In-process наш сервер
на реальном v2, бот стоит (`crates/parity/tests/join_window_ours.rs`): при
R=10 отправлено **473**, все в окне, ни одного вне, **0** отсутствующих в v2,
порядок элемент-в-элемент равен `net::window`; при R=8 — **289** (квадрат).
Множество R=10 совпало с ванильным контролем **473/473** (0 расхождений в
обе стороны, `analyze.py shape-join --list`); payload'ы не сверялись. Порядок
внутри первой порции у ванили иной, но вторичный ключ по трейсу **не
установлен** — оставлен наш `(dx2+dz2, x, z)`. Спец-флаг проверки режима для
нашего сервера не понадобился (`JoinWindow`, как `Preload`, её не применяет).

## Пул регионов: владение каналом, барьер, merge по `region_id` (M4.3 A2)

**Решение.** Многопоточное ядро — `std::thread`-пул (`K` воркеров) без
новых `Mutex`/`RwLock` в горячем пути: регион **передаётся по владению**
(mpsc), воркер тикает и возвращает его; планировщик ждёт ровно столько
результатов, сколько отправил (**барьер**), и объединяет `TickOutcome` в
порядке `region_id`, а не завершения. `Region::tick` обходит игроков в
порядке id — иначе порядок `HashMap` ломал бы детерминизм merge.

**Параметр `K`.** `server.toml: workers` (default `ядра−2`, минимум 1) →
`GameConfig.workers`; `0` = пула нет, регионы тикаются последовательно на
потоке планировщика (поведение M4.1/M4.2). `net::serve` остаётся
последовательным (`GameConfig::default()`), живой сервер идёт через
`net::serve_with`.

**Inline против передачи на одном регионе — [гипотеза] до M4.6.** При
`≤1` регионе тик **inline** (без передачи воркеру). Замер (20000 тактов,
release, один регион): inline p50 0.100 / p99 0.100 мкс, передача p50
0.700 / p99 1.900 мкс. Разница мала на фоне периода 50 мс; окончательное
решение о пороге — M4.6 (там же проверка приоритета потока тика).

**Тесты.** (а) K=0/1/4, 8 регионов — равный `TickOutcome`; (б) merge не
зависит от порядка завершения (задержка 50 мс в регионе 0); (в) пул
останавливается < 2 с; (г) 1000 пустых тактов K=4 (4 региона): drift
0.597 мс, p99 jitter 1.030 мс. Замеры — в `ARCH-M4.md` §6.

**Проверка.** `net::game::tests::{k_zero_one_and_four_merge_the_same_outcome_for_eight_regions,
the_merge_order_does_not_depend_on_the_completion_order,
the_region_pool_stops_within_two_seconds, a_thousand_idle_pooled_ticks_do_not_drift}`;
`net::game::pool`, `net::game::scheduler`.

## Часть B M4.3: карта регионов, `Transfer` после барьера, `region_side = 0`

**Решение.** Регион — квадрат `region_side` чанков; `region_side = 0`
(значение по умолчанию) означает **разбиения нет**: весь мир — регион 0,
поведение до M4.3, поэтому живой сервер при дефолте не меняется. Сторону
решает бенчмарк M4.6 (D3). Игрок принадлежит региону своего чанка;
планировщик держит индекс `player_id → region_id`. Движение через границу
применяется **в регионе-источнике в этом такте**; регион возвращает
`Transfer { player, from, to, seq }`, а планировщик применяет все `Transfer`
**после барьера** в порядке `(from, seq)` (тай-брейк — `player_id`),
перенося `Player` целиком по владению. Детерминизм: `BTreeMap<PlayerId, _>`
в регионе, свой `seq` на событие; строка реплея `kind="transfer"`
`{player, from, to}`; строки `join`/`move`/`teleport_ack`/`quit` не менялись.

**«Исходящее» в M4.3 — результаты такта, не пакеты.** Настоящих исходящих
у тика ещё нет (стриминг `StreamChunks` — M4.4), поэтому канонический
«исходящий транскрипт» = результаты такта в порядке `(tick, region, seq)`
(`TickOutcome::transcript`); сверка настоящих пакетов байт-в-байт — в M4.4.

**Почему дефолт 0, а не тайл от начала координат.** Дефолт 0 — явный
выключатель: до бенчмарка M4.6 ненулевой тайл по умолчанию менял бы живое
поведение без данных о выигрыше (на реальном шаблоне выигрыша и нет — он
влезает в один регион, риск б в `ARCH-M4.md` §7).

**Проверка.** `net::game::grid::tests` (дефолт 0, деление вниз);
`net::game::region_tests` (сценарии а–д); `net::game::replay_tests`
(транскрипт дважды байт-в-байт, при K=0/1/4/8, плейбек журнала воспроизводит
прогон). Результаты и проверенные против гипотезы пункты — `ARCH-M4.md` §6.
