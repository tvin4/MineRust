# playerdata — план и реализация (Шаг 17d → 18a)

**Статус: реализовано в Шаге 18a.** Сервер читает файл при входе, пишет его на
выходе, по автосейву и на остановке; формат — ванильный NBT. План ниже
оставлен как история решений; фактическая реализация, API и расхождения —
§11.

Задача: сохранять состояние игрока между заходами — позицию, поворот,
здоровье/еду, режим игры — в формате, совместимом с ванильным, в **отдельной**
папке сохранений (никогда в шаблоне мира).

## 1. Факты, на которые опирается план

### 1.1 Файл на диске

- Ваниль хранит игрока в `players/data/<uuid>.dat`: **gzip-сжатый NBT с
  именованным корнем** (байт типа `0x0A`, длина имени, имя, полезная нагрузка).
  Шаблон `E:\MineRust-data\world-template-v3` содержит ровно один такой файл —
  `players/data/ff1070c9-7b1a-3e30-a01e-89fe7a426681.dat` (778 Б, ParityBot).
- Поля этого файла (прочитаны штатным NBT-ридером): `Pos` (3 double),
  `Rotation` (2 float: yaw, pitch), `Health`, `foodLevel`,
  `foodSaturationLevel`, `playerGameType`, `Dimension`, `OnGround`, `Air`,
  `XpLevel`, `XpTotal`, `DataVersion` 5023, `abilities`, `Inventory`,
  `EnderItems`, `attributes`, `Brain`, `recipeBook`, `Motion`, `UUID`.
- **Имя файла — не UUID как в чате:** первые три группы UUID пишутся
  байтами в обратном порядке (`08059210-d8d5-ed3e-...` →
  `10920508-d5d8-3eed-...`); `Rotation` — TAG_List из двух float BE. Это уже
  зафиксировано харнессом (`tools/testclient/README.md`, §«Находки отладки»,
  п. 4) и должно быть в writer'е, иначе S1 не найдёт файл.
- Для Alice файла нет: ни один прогон не сохранял игрока (у ванильных прогонов
  каталог мира — временный и удаляется, у нашего сервера записи нет вовсе).
  Значит новый игрок должен получать **минимальный корректный** файл при
  первом выходе, а не копию чужого.

### 1.2 Что уже есть в коде

- Чтение gzip-диска: `world::read_world_document(path)` — публичная функция,
  `fs::read` → `GzDecoder` → `nbt::decode_disk` (пропускает имя корня и отдаёт
  значение в `protocol::NbtTag::decode_network`). Ею уже пользуется аудит
  шаблона (`crates/world/tests/template_docs.rs`).
- Записи дискового NBT **нет**: `protocol::NbtTag` умеет `encode_network`
  (тип + payload, без имени корня) и `encode_entry` (элемент компаунда); нужен
  маленький `encode_disk` = `0x0A` + `u16` длина имени + имя + payload, затем
  `flate2::GzEncoder`. `flate2` в `crates/world` уже используется (тесты
  `level.rs`).
- `set_health` в нашем протоколе не реализован: в `packets.json` это
  clientbound play id **106**; поля — `health: f32`, `food: varint`,
  `saturation: f32` (по трейсу ванили). Пакета `player_rotation` при входе
  ваниль **не** шлёт — поворот лежит в `player_position` (0x49/73).

### 1.3 Что ваниль шлёт при входе (трейс S7, `2026-11-14_s7-sneak-final`)

| соединение | первый `player_position` | `set_health` |
|---|---|---|
| conn-1 (Alice, сохранённый игрок) | `(96.5, 128.0, -10.3)`, yaw 0, pitch 0 | 15.666667, food 17, sat 0 |
| conn-2 (Bob, новый игрок) | `(96.5, 145.0, -31.5)`, yaw 0, pitch 0 | 20, food 20, sat 5 |

Оба пакета ваниль шлёт в обоих случаях; различаются только значения. Значит
наш join должен слать `player_position` с сохранёнными позицией и поворотом и
**добавить** `set_health` (сейчас мы его не шлём вовсе), в том же порядке:
сначала `player_position`, затем `set_health`.

В этом прогоне сохранённый поворот был 0/0, поэтому трейс не доказывает
восстановление ненулевого угла; для этого в харнессе уже есть `Invoke-S1`
(поворот после перезахода) — сейчас он фиксирует «наш сервер playerdata не
пишет».

## 2. Формат: варианты

| вариант | что это | плюсы | минусы | размер |
|---|---|---|---|---|
| **A. Ванильный NBT** | `players/data/<uuid>.dat`, gzip NBT | читается ванильными инструментами и нашим ридером; S1 проверяет именно его; можно читать файл шаблона | нужен writer и отображение полей; незнакомые теги надо сохранять | средний |
| B. Свой формат | JSON/бинарный файл `players/<uuid>.json` | проще писать | несовместимо с S1/ванилью, нужен конвертер | малый |
| C. Без сохранения | — | ничего делать не надо | S1 остаётся красным, игрок каждый раз на спавне | нет |

**Предложение: A.** Формат уже описан фактами выше, ридер есть, а харнесс
проверяет именно `.dat`.

## 3. Где хранить (жёсткие правила владельца)

- **Отдельная папка сохранений**, настраиваемая (предложение:
  `save_dir = 'E:\MineRust-data\worlds\minecraft-v3'`), внутри неё —
  `players/data/<uuid>.dat`.
- **Никогда** шаблон `E:\MineRust-data\world-template-v3` и ничего внутри него:
  `world_dir` остаётся read-only источником чанков/`level.dat`.
- **Проверка пути перед записью:** канонизировать `save_dir` (создав её) и
  `world_dir`; отказ с ошибкой конфига, если пути равны или `save_dir` лежит
  внутри шаблона. Тест на оба случая + «соседняя папка разрешена».
- Папка создаётся при старте; отсутствие прав — ошибка старта, а не тихий
  пропуск сохранения.
- Когда появится шаг 18 (сохранение блоков), папка мира и playerdata будут
  жить в одном `save_dir`; сейчас playerdata — единственный её житель.

## 4. Какие поля сохраняем

| поле | ключ NBT | источник | примечание |
|---|---|---|---|
| позиция | `Pos` (3 double) | `player_position`/move-пакеты | ноги игрока |
| поворот | `Rotation` (2 float) | те же пакеты | yaw, pitch |
| здоровье | `Health` (float) | `set_health` | 0..20 |
| еда | `foodLevel` (int), `foodSaturationLevel` (float) | `set_health` | 0..20 |
| режим | `playerGameType` (int) | конфиг/игрок | 0 survival, 1 creative |
| измерение | `Dimension` (string) | константа | `minecraft:overworld` |
| прочее | `OnGround`, `Air`, `Motion`, `FallDistance`, `XpLevel`, `XpTotal`, `DataVersion` | расчёт/константы | `DataVersion` 5023, как в шаблоне |
| инвентарь и т.п. | `Inventory`, `EnderItems`, `abilities`, `attributes` | из файла, если он есть | у нового игрока отсутствуют — предметы не моделируются |

Правило записи: если файл уже есть — **читаем, обновляем известные поля,
остальные теги пишем обратно без изменений** (чтобы не терять чужие данные);
если файла нет — синтезируем минимальный компаунд (без инвентаря).

## 5. Пакеты при входе

- `player_position` (id 73/0x49): сохранённые позиция и поворот, `teleport_id`
  свой, `flags = 0`; для нового игрока — спавн (как сейчас) и угол 0/0.
- `set_health` (id 106, новый пакет): сохранённые `health`, `food`,
  `saturation`; для нового игрока — 20/20/5 (ваниль; насыщение 5 у нового).
- Порядок как в трейсе: `player_position` раньше `set_health`.
- Остальной join-набор не меняется. Проверка порядка — parity/трейс.

## 6. Когда сохранять

1. **На выходе игрока** (disconnect) — ванильный путь; пишем один файл.
2. **Периодически** — ванильный автосейв раз в 6000 тиков (5 мин);
   интервал — параметр конфига.
3. **При остановке сервера** — graceful shutdown сохраняет всех.
4. **Атомарно:** пишем `<uuid>.dat.tmp` в той же папке, `flush`+`fsync`,
   затем `rename` поверх; частично перезаписанный файл невозможен.
5. Один владелец данных: запись делает игровой поток (или отдельная задача по
   сообщению). Никаких `Mutex` в тике — правило `docs/DECISIONS.md`.

## 7. Связь с изменениями блоков в памяти

Playerdata **не** сохраняет мир. Сломанные блоки и `dev_geometry` живут только
в `ChunkStore` и исчезают при перезапуске — это шаг 18 (сохранение чанков).
Файлы игроков лежат в том же `save_dir`, но пишутся независимо; в 17d связи
между ними нет.

## 8. Тесты

Юнит:

- NBT-диск: минимальный компаунд → `encode_disk` → gzip → `read_world_document`
  → те же поля; имя корня (пустое) на месте.
- Сохранение незнакомых тегов: взять файл шаблона (ParityBot), прочитать,
  изменить `Pos`/`Rotation`, записать, прочитать — `Inventory`/`abilities` не
  потеряны.
- Проверка пути: `save_dir == world_dir` и `save_dir` внутри шаблона — ошибка;
  соседняя папка — ок.
- Валидация значений: `Health` 0..20, `foodLevel` 0..20, `Pos`/`Rotation`
  конечные (NaN/∞ отклоняются), `DataVersion` 5023.

Интеграционные (сервер):

- Вход без файла → спавн, 20/20, на выходе появляется `.dat`.
- Вход с файлом → `player_position` несёт сохранённые позицию/поворот,
  `set_health` — сохранённые значения.
- Выход → файл gzip, корень-компаунд, `DataVersion` 5023; повторный вход
  возвращает то же.
- Два игрока: файлы по UUID, без перекрёстного влияния.

Харнесс:

- `Invoke-S1` на нашем сервере: поворот переживает перезаход (сейчас —
  записанный пробел).

Ручная сценарий владельца: зайти, пройти/повернуться, выйти, зайти снова —
позиция и поворот совпадают; здоровье/еда — те же, что были (урона в игре
пока нет).

## 9. Размер и риски

- **A: средний** — writer NBT (≈100 строк + тесты), чтение/запись при
  join/quit, новый пакет `set_health`, конфиг и проверка пути; затрагивает
  жизненный цикл соединения (join и disconnect).
- **B: малый**, но ломает совместимость и S1.
- **C: нулевой**, S1 красный.

Риски: случайная запись в шаблон (закрывается проверкой пути и тестом);
несовпадение UUID при offline/online login; смена `DataVersion` при обновлении
игры; потеря незнакомых тегов у синтезированных файлов (инвентаря нет —
ожидаемо); здоровье 0/смерть и респавн не моделируются; конкурентная запись
двух соединений одного UUID (закрывается владением данных).

## 10. Вопросы владельцу (ответы получены 17.11.2026)

1. **Папка.** `save_dir = E:\MineRust-data\worlds\minecraft-v3`, одна папка на
   мир; внутри — `players/data/<uuid>.dat`. `save_dir` не может быть шаблоном,
   лежать внутри шаблона или внутри `vanilla\world` стенда. Тесты и
   scenario-runner используют отдельную `save_dir` внутри каталога прогона.
2. **Полнота NBT.** Существующий файл читаем, известные поля обновляем,
   незнакомые теги пишем обратно; новый игрок — минимальный компаунд;
   `DataVersion` — из `level.dat` шаблона (или ванильного `.dat`). `Dimension`
   не overworld → `warn` и спавн.
3. **Здоровье/еда.** Значения как в файле; новый игрок 20/20/5; `Health <= 0`
   или не число → 20 + `warn` (смерть вне шага).
4. **Режим игры.** Приоритет у конфига; `force_gamemode` (default `true`) —
   `true`: режим из конфига, `false`: из файла, если есть.
5. **Триггеры сохранения.** Выход + автосейв (`autosave_interval_ticks`,
   default 6000) + остановка. Запись не в тик-потоке: тик делает снимок и
   отправляет его потоку записи; на остановке — flush и join с таймаутом.
   Порядок записей одного игрока сохраняется; атомарно `.tmp` + rename.
6. **`players/stats` и `players/advancements`** не пишем.
7. **Смерть и респавн** вне шага.

## 11. Реализация (Шаг 18a, 17.11.2026)

### 11.1 Крейт `playerdata`

`crates/playerdata` — единственный владелец файлов; API:

- `Store::open(save_dir, data_version, forbidden: &[(&str, &Path)])` —
  проверяет путь (до создания папки и после), создаёт
  `<save_dir>/players/data`. `Store::read(uuid) -> Result<Option<SavedPlayer>,
  PlayerdataError>`: `None` — файла нет; битый файл — ошибка чтения (вызывающий
  логирует и играет как новый). `Store::write(&Snapshot)` обновляет известные
  поля, сохраняя незнакомые теги, и пишет атомарно (`<uuid>.dat.tmp` →
  `sync_all` → `rename`). `playerdata::file_name(uuid)` — ванильное имя файла
  (первые три группы байтов UUID реверсируются).
- `spawn(store, capacity) -> (Sink, Writer)`; `Sink::snapshot` — неблокирующий
  `try_send` (`false` = очередь полна/поток ушёл); `Writer::shutdown(timeout)`
  — `Shutdown` за pending-записями, join с таймаутом
  (`ShutdownTimeout`/`WriterGone`).
- Ошибки: `Io`, `Corrupt`, `ForbiddenPath`, `InvalidValue`, `ShutdownTimeout`,
  `WriterGone`, `Spawn`. Ошибка записи не роняет сервер.

### 11.2 Сервер и конфиг

- `server.toml`: `save_dir` (отсутствует → сохранение выключено + одно
  `warn`), `force_gamemode` (default `true`), `autosave_interval_ticks`
  (default 6000, `0` — без периодической записи). `DataVersion` читается из
  `level.dat` мира. Проверка `save_dir` (шаблон/стенд) и открытие store
  происходят **до bind**; при остановке — `Writer::shutdown(5s)`.
- `net::game::PlayerdataRuntime { store, sink, force_gamemode,
  autosave_interval_ticks }` живёт в `GameConfig`/`GameHandle`. Вход читает
  файл через `spawn_blocking`; `ToGame::Quit` и автосейв кладут снапшоты в
  очередь; игровой цикл делает финальный `save_all` перед выходом.
- Вход: `Entry { pose, health, food, saturation }`; `resolve_entry`
  применяет сохранённую позу только без `spawn_override` и в overworld;
  `resolve_game_mode` реализует приоритет конфига/файла. Join шлёт
  `player_position` с сохранёнными позицией и поворотом, затем `set_health`
  (id 106) с health/food/saturation. `SetCenterChunk` строится от входной
  позы.

### 11.3 Что проверяется тестами

- `playerdata`: round-trip gzip-документа, сохранение незнакомых тегов,
  повреждённый файл, `Health <= 0`, не-overworld `Dimension`, имена файлов,
  защита пути (в шаблоне — ошибка; соседняя папка — ок), полная очередь,
  `shutdown` с дренажом, ошибка записи не останавливает поток.
- `net`: `resolve_entry` (overworld/non-overworld/spawn override/нет файла/
  on-ground), `resolve_game_mode` (force on/off/нет режима/нет store),
  `send_join` (телепорт в сохранённую позу, `set_health` 7-м пакетом),
  `snapshot_of`, quit-сейв в файл, автосейв двух игроков.
- `server`: `--test join` и `--test status` читают `set_health` после
  телепорта (новый игрок 20/20/5). `cargo test --workspace` и clippy
  `-D warnings` зелёные.

### 11.4 Чего нет и что не установлено

- **S13 закрыт (Шаг 19a):** живой сценарий «вход → движение/поворот →
  выход → повторный вход» запущен 17.11.2026 (`2026-11-17_s13-live-r7`,
  0 failed) — итоги в §12.
- Смерть/респавн, урон и голод не моделируются; здоровье/еда за сессию не
  меняются, файл хранит входные значения.
- Online-login (UUID из Mojang) не реализован — имя файла строится от
  offline UUID; при переходе на online-режим UUID станет другим.
- Инвентарь/эффекты/достижения не пишутся (не моделируются); у нового файла
  их нет — клиент воспринимает это как пустой инвентарь.
- Два одновременных соединения с одним именем не защищены на уровне логина
  (очередь записи одна, но оба соединения — разные `PlayerId`).

  сохранение. Тест `the_file_name_matches_the_vanilla_player_file` (включая
  файл ParityBot из шаблона).
- **Потеря поворота.** Клиент шлёт `move_player_rot` и `move_player_pos`
  отдельными пакетами в одном тике; слот «последний пакет» хранил только
  `pos`, и углы терялись (`Rotation=0,0`). Теперь пакет с углами живёт во
  втором слоте (`MoveSlot::take_rotation`) и применяется перед пакетом
  движения (`PlayerPos::apply_rotation`); 3 теста в `net`.
- **Проверка (5) была вакуумной.** `save_all` вызывается после
  `after_entities`, поэтому его время не входило в `phases_total_us`, а
  парсер лог-строк не снимал байт `ESC` от ANSI-раскраски и читал нули.
  Добавлена строка `autosave queued` (`tick`, `save_us`, `players`) — на тике
  только снапшот и `try_send`, диск пишет отдельный поток. Проверка смотрит
  именно эту величину; `phases_total_us` остаётся контекстом (в него входят
  доставка чанков и пробуждение ОС, не запись).

**Строка для `server.toml`** (одна папка на мир, вне шаблона и
`vanilla\world`; та же строка в `README.md`):


## 13. Риски и открытые вопросы (Шаг 19c; решения и код — Шаг 20a)

### 13.1 Два соединения с одним именем (решено, Шаг 20a)

**Было (Шаг 19c).** Логин не проверял, занято ли имя: оба соединения
получали один и тот же offline UUID (`protocol::offline_uuid`), читали и
писали **один** файл, а в памяти это были два разных `PlayerId` с
независимыми состояниями. Файл поочерёдно отражал то одно, то другое
состояние — «последний записал — победил».

**Поведение ванили (S15, снято с трейса).** Прогон
`E:\MineRust-data\autotests\2026-11-17_s15-vanilla-r2`: второй вход с тем
же именем отключает **старое** соединение, новое остаётся. Старый клиент
вышел в меню за ~2 с до появления нового в логе сервера; в трейсе старого
соединения `minecraft:disconnect` (play id 32) с NBT-причиной
`{"translate":"multiplayer.disconnect.duplicate_login"}`, и это последний
пакет соединения.

**Сделано (Шаг 20a), по трейсу.** `ToGame::Join` сравнивает offline UUID
нового игрока с UUID всех онлайн-игроков; у совпавшего старого:
`ServerMessage::Disconnect { DuplicateLogin }` → соединение пишет
play-`disconnect` с теми же байтами, что ваниль, и закрывается; игрок
сохраняется в файл и удаляется из региона. Новый игрок входит как обычно.
Побайтный тест `disconnect_play_matches_the_s15_duplicate_login_bytes`
(`crates/protocol`), тест `a_second_login_with_the_same_name_kicks_the_first`
(`crates/net`). Живой прогон на нашем сервере
`2026-11-17_s15-ours-r1` — **0 failed**: старый клиент выброшен, новый
остался, в трейсе старого ровно один `disconnect` с той же причиной
(`0a0800097472616e736c61746500266d756c7469706c617965722e646973636f6e6e6563742e6475706c69636174655f6c6f67696e00`).

**Что осталось.** Кик не пишет системное сообщение «игрок вышел» (чата у
нас нет); сравнение времени между соединениями по `read_ms` некорректно
(у каждого соединения свой прокси-трейс), поэтому «кик раньше нового
логина» проверяется только по ванильному логу, а не в S15.

### 13.2 Потери при падении между автосейвами

- Запись идёт только на выход игрока, автосейв и остановку сервера.
  Жёсткое убийство процесса (`taskkill /F`, BSOD, пропадание питания)
  теряет всё, что накопилось после последнего автосейва.
- Окно потерь = `autosave_interval_ticks` (default 6000 тиков ≈ 5 мин при
  20 TPS) + задержка очереди (обычно миллисекунды). Новый игрок, ушедший
  до первого автосейва, файла не оставляет вовсе.
- Каждый файл пишется атомарно (`.dat.tmp` → `sync_all` → `rename`),
  затем синхронизируется каталог (`sync_dir`): на Unix это `fsync`
  каталога, на Windows вызов — no-op (журнал NTFS сам фиксирует переименование;
  открыть каталог для `fsync` там нельзя). Тест
  `a_write_syncs_its_directory_where_supported` проходит на обеих
  платформах и не падает.
- Уменьшение интервала сужает окно, но учащает I/O; I/O и так вне
  тик-потока (отдельный поток записи), поэтому цена — только диск. Решение
  владельца (Шаг 20a): default **6000 тиков оставлен**.

### 13.3 Смена `save_dir` между запусками

- `save_dir` читается один раз при старте; store открывается на весь
  запуск. Миграции между каталогами нет: старые файлы остаются в прежней
  папке, игроки в новом каталоге входят как новые (спавн, 20/20/5, режим
  из конфига).
- Если чередовать каталоги, состояния расходятся: «последняя запись в
  каждый каталог» нигде не сливается.
- Проверяется только запрет на шаблон и `vanilla\world`. «Чужой» непустой
  каталог не детектируется как чужой мир, но теперь это видно: при
  создании в пустом каталоге сервер пишет маркер `minerust-save.json`
  (`format: "minerust-save"`, `version: 1`, `data_version` мира). Непустой
  каталог без маркера используется, но сервер пишет `warn` и **не**
  присваивает его; битый маркер или чужая версия — тоже `warn` и работа
  продолжается. Тесты `open_writes_the_marker_into_an_empty_save_root`,
  `open_tolerates_a_non_empty_root_without_a_marker`,
  `open_tolerates_a_damaged_or_future_marker`.
- Рекомендация: одна папка на мир, зафиксированная в `server.toml`;
  перенос — вручную скопировать `players/data` (и маркер) при
  остановленном сервере. Автоматической миграции нет.

### 13.4 Формат UUID (offline vs online)

- Сейчас поддерживается только offline: UUID = MD5 от
  `OfflinePlayer:<name>` с битами version 3 и variant RFC 4122
  (`protocol::offline_uuid`). Имя файла — байты UUID по порядку, поэтому
  первые три группы в имени файла «перевёрнуты» относительно строки UUID
  (`08059210-d8d5-ed3e-...` → `10920508-d5d8-3eed-...`); это проверено по
  файлам самого ванильного сервера 26.3.
- Online-login не реализован. При переходе на него UUID придёт от Mojang
  (version 4), имя файла станет другим, и существующие offline-файлы не
  найдутся: игрок войдёт как новый, пока не сделана миграция.
- UUID считается от имени в том виде, в каком оно пришло; смена регистра
  даёт другой UUID (для offline — следствие формулы; совпадает ли регистр
  с ванильным — не проверялось).
- `players/stats` и `players/advancements` мы не пишем; ванильный клиент
  может создать их сам.
