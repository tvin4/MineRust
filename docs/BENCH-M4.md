# BENCH-M4 — результаты M4.6 (замер механизма тика и стриминга)

Все замеры: Ryzen 5 2600X, 6 ядер / 12 логических (SMT), Windows, release-сборка.
Полные отчёты в `target/bench/*.md` (не коммитятся); здесь — агрегаты.

**Оговорка SMT:** K=12 превышает число физических ядер (6). Результаты K=12 —
это деление 6 физических ядер на 12 логических потоков, не «12 полноценных воркеров».

**Условия:** фоновой CPU перед серией A2.4 — ~27% (машина владельца с активными
процессами); перед A3 — не измерить чисто (сам замер грузит CPU). Владельца
просили не запускать тяжёлые программы во время замеров.

## 1. Capacity (W1, реальный тик; планировщик без пауз)

Игроки ходят 0.25 блока/тик через реальный `MoveSlot` → `Region::tick` (декод,
StreamChunks, Transfer). Warm-up 100 тиков отброшен, измерено 200 тиков.
Конфиг: region_side=64 → 10×10 сетка регионов, 64 игрока с шагом 8 чанков,
W1 = без добавленной нагрузки.

| run | p50 µs | p99 µs | max µs |
|---|---|---|---|
| K0 (inline) | 6 | 6224 | 10234 |
| K2 | 6 | 6302 | 9952 |
| K6 | 6 | 6734 | 9291 |
| K10 | 6 | 5586 | 5947 |
| K12 (SMT) | 7 | 6043 | 10432 |

W1 на реальном коде тика дешёв: **p50 = 6 µs при любом K**; p99 (5.6–6.7 мс)
и max — всплески первого тика после warm-up (джиттер, не работа). Разница
K=0 vs K=2..12 в пределах разброса повторов.

**Различие K=0 vs K>0 на W1: не установлено** (разница меньше разброса повторов).

## 2. Capacity (W2, синтетическая нагрузка — потолок масштабируемости)

W2 = busy-loop S µs на регион за тик. **Не игровая скорость** — это потолок
механизма пула. Тот же grid (side=64 → ~100 регионов), 64 игрока.

| S=200 µs/регион | p50 µs | p99 µs | тиков/с |
|---|---|---|---|
| K2 | 211 | 7464 | 3032 |
| K6 | 209 | 6201 | 3372 |
| K10 | 208 | 5869 | 3400 |

| S=1000 µs/регион | p50 µs | p99 µs | тиков/с |
|---|---|---|---|
| K2 | 1011 | 8826 | 874 |
| K6 | 1009 | 6470 | 915 |
| K10 | 1010 | 7148 | 902 |

Чтение:

- p50 ≈ S в обоих случаях — один регион тикает за своё S, параллелизм
  распределяет регионы по воркерам (иначе p50 был бы ~S×регионов/K);
- тиков/с ~3400 при S=200 и ~900 при S=1000: пул держит темп, пока
  `регионы × S / K ≲ 50 мс`; при S=1000 и ~100 регионах K=2 уже на границе
  (100 × 1 мс / 2 = 50 мс = ровно тик) — отсюда p99 8.8 мс поверх;
- K10 vs K6: выигрыш минимален на 6 физических ядрах (SMT-переподписка).

**Потолок механизма подтверждён замером:** масштабирование ограничено
физическими ядрами, а не числом регионов; K > физ.ядер не даёт выигрыша.

|---|---|---|---|---|
| 2 бота, K=2 (CI smoke) | <100 | ~19 | 0 | 0 |

## 4. Стриминг (A2.3, критерий M4.4 «100+ чанков»)

Один бот, синтетический плоский мир 288×288 чанков (заведомо шире окна),
прямая ходьба +x, 1.0 блок/тик, 2000 шагов (~100 с):

- **125 пересечений границ чанка** (критерий 120+) — закрыт;
- получено 3348 чанков, 127 батчей, 126 смен центра, 2875 forget;
- **инвариант окна: live set бота (473) == window(центр (125,0), R=10) (473),
  0 чанков вне окна, 0 отсутствующих** — чанк не теряется и не забывается;
- max batch depth (по счётчику бота) — 464;
- тик сервера: p50 0.051 / p99 0.30 / max 2.5 мс; late_ticks 0; drift 0.5 мс.

Код бота (бот-бухгалтерия) не влияет на инвариант сервера: серверные
`debug_assert!` внутри `PendingBatch::within_window` проверяли то же самое
на каждом шаге. Инвариант закрыт с обеих сторон.

Формат: `load <N> <K> <SIDE> 60`; бот входит (~109 мс каждый), затем 60 с

Наблюдения:

- **0 киков во всех 24 заездах**, включая 200 ботов (N=200 не упёрся — лимит
  не найден на этой матрице; узкое место CPU машины владельца, фон ~27%);
- join-фаза линейна по N: ~109 мс/бот (10 → 1.1 с, 200 → 21.8 с);
- тик p50 растёт линейно по N (0.03→0.28 мс на 10→200 ботов) — это обход
  200 MoveSlot'ов за тик, не узкое место пула;
- p99 (5–13 мс) и max (10–30 мс) — всплески на join-фазе и пересборке окон;
  на установившейся ходьбе p50/p99 остаются в единицах микросекунд;
- side=16 и side=1 показывают близкие p99 — при N ≤ 200 и такой разреженности
  игроков пул регионов на механизме тика ничего не даёт и не портит;
  разница — в шуме.

## 6. Приоритет тик-потока (A3)

`GameConfig.tick_thread_priority` (default off; Windows,
`THREAD_PRIORITY_ABOVE_NORMAL`). Сценарий: 100 ботов + 8 busy-потоков,
paced W1, 20 с заезд, 3 повтора на половину. Полный отчёт:
`target/bench/priority-*.md`.

| Повтор | A (off): p50/p99/max мс, late | B (on): p50/p99/max мс, late |
|---|---|---|
| 1 | 0.189 / 9.5 / 24.9, **27** | 0.193 / 7.3 / 11.6, 1 |
| 2 | 0.199 / 13.6 / 28.2, 4 | 0.194 / 3.2 / 17.6, 0 |
| 3 | 0.196 / 8.2 / 42.0, 10 | 0.183 / 8.8 / 11.8, 0 |

Вердикт по правилу «различие засчитывается, только если превышает разброс
внутри повторов»:

- **late_ticks (тик с опозданием > 20 мс): различие установлено.** Худший
  повтор с флагом (1) лучше лучшего без флага (4). Под contention (8 busy-
  потоков) приоритет тик-потока практически убирает опоздания.
- **tick p99: различие не установлено** (диапазоны 8.2–13.6 и 3.2–8.8 мс
  пересекаются).
- **tick p50: не изменился** (~0.19 мс в обеих половинах) — сам тик не
  ускоряется, флаг влияет только на планирование пробуждений под нагрузкой.

**Решение (D7):** флаг остаётся в конфиге, default off. Рекомендация:
включать на нагруженных машинах с фоновыми процессами; на простаивающей
машине эффекта нет (серия A2.4 без busy-потоков давала 0–1 late тик везде).

## 7. Решения по данным (D3/D5/D6)

- **D5 (дефолт K):** `available_parallelism − 2` остаётся дефолтом. На W1
  пул ничего не даёт (тик дешёв), на W2 выигрыш пропорционален K. K = cores−2
  — разумный компромисс: пул не отбирает ядра у tokio-рантайма и не уходит в
  SMT-переподписку.
- **D3 (region_side):** при N ≤ 200 и разреженных игроках разница side=1
  (один регион) и side=16 — в пределах шума. Дефолт 0 (без разбиения) до
  тех пор, пока реальный мир не станет узким местом; решение пересмотреть
  по данным реального тика, не W2.
- **D6 (CI):** smoke-тест бенча (2 бота, K=2, ~1.25 с) в CI; полные серии —
  только вручную (`cargo run -p bench -- capacity|paced|streaming|load|priority`).
- **D7 (приоритет потока):** default off; вердикт — раздел 6 (late_ticks
  улучшаются под contention, p50/p99 — нет).
- **Лимит игроков на 20 TPS:** не достигнут в этой матрице (200 ботов —
  0 киков, p99 тика ~12 мс). Оценка сверху: на этом железе тик W1 с сетью
  держит 20 TPS при p50 ≈ 0.3 мс на 200 ботов — узкое место будет не в тике,
  а в коде мира/диска, которого бенч не трогает.

## 8. Что бенч не измеряет

- Реальный генератор мира, освещение, диск (синтетический плоский мир);
- реальную сетевую задержку и TCP-стек за пределами localhost;
- ванильный сервер (сравнение скоростей — задача parity-тестов, не M4.6);
- W2 — не игровая скорость, только потолок механизма пула.
