## 0. Как устроено сейчас (основа изменений)

- `net::serve` принимает соединения и на каждое спавнит собственную
  tokio-задачу → `handle_connection` → `play_state`. В `play_state`:
  join-последовательность (`join::send_join`), фоновое чтение фреймов в
  mpsc-канал, `select!` с ветками keep-alive / ответа загрузчика /
  отправки батча / входящих фреймов; пакеты движения распознаются, но
  пишутся `trace!("movement received, ignored")` — **позиции игрока не
  существуют**.
- Мир: `server::build_world` создаёт `TemplateWorld` (кэш
  `ready: OnceLock<Arc<Vec<LevelChunkWithLight>>>`) и пул `net::loader`
  (2 именованных потока, ограниченные очереди по 4, ответ через
  oneshot), `serve` раздаёт `Loader` клонами. `play_state` читает батч
  один раз на вход и больше со взаимодействия с миром не имеет.
- Отправка чанков — `play/batch.rs`: `PendingBatch`, состояния
  First → AwaitPace(1 с) → Pace(50 мс), первая порция 9, по
  `chunk_batch_received` — `ceil(rate)` за тик (п.5 A2, `6d113a8`).
- Игрового потока и тика **нет вовсе**: время обслуживается только
  интервалами внутри отдельных задач (keep-alive 15 с, тика-пути нет).

**Что должно измениться.** Состояние игроков и мира переезжает в
один игровой поток (тик), соединение становится тонким кодеком:

```
 TcpStream                      игровой поток (20 TPS)
 ┌──────────────┐  mpsc(N)     ┌──────────────────────────────┐
 │ play_state:  │  Move{pos}:  │ Registry игроков (owner:      │
 │  decode/encode├────────────►│  HashMap<id, Player>),        │
 │  keep-alive  │◄────────────┤  окна стриминга, кэш мира,    │
 │  batch.rs    │  Outbound:   │  очередь сообщений регионов   │
 └──────────────┘  Packet(..)  └──────────────────────────────┘
        ▲ oneshot: join/quit                    │
        └──────── load payload (существующий net::loader)
```

Сообщения (bounded-каналы, размер задаётся: переполнение = backpressure
на приёме, а не блокировка тика — **[гипотеза]**, точный размер даст
бенч):

- вверх: `Join { id, name, view_distance, pos }`,
  `TeleportAck { id, teleport_id }`, `Quit { id }` — надёжные сообщения;
  `Move { id, pos, yaw, pitch, on_ground }` — не сообщение в очередь, а
  слот «последняя позиция игрока» в его состоянии (клиент шлёт позицию
  20 раз в секунду, тику нужна последняя, старая перезаписывается);
- вниз: `StreamChunks { id, add, remove }` — тик решает, какие чанки
  (payload, `Arc`) добавить в окно игрока и какие убрать; соединение
  берёт `Arc`-payload из кэша и шлёт их через существующий `batch.rs`
  (пейсинг и порядок — §4). И `Send { id, packet }` — реактивные
  исходящие вне тика (телепорт-подтверждение, сообщения об ошибке
  чтения).

**Политика медленного клиента (явно).** Исходящая очередь одного
клиента ограничена (`try_send`-семантика, размер задаётся конфигом).
Если очередь переполнилась — **тик не блокируется и не ждёт**: клиенту
уходит kick с причиной «send queue overflow» и разрыв. Это решение,
а не побочный эффект: одна медленная TCP-задача не может остановить
весь мир.

**Надёжный путь (взамен «узкого пути с приоритетом»).** `Join`, `Quit`
и `TeleportAck` соединение отправляет тику через `send().await`:
тормозит только эта сетевая задача, сообщение не теряется. Тик читает
входящее через `try_recv` и никогда не ждёт.

**Переполнение исходящей очереди клиента** — это превышение **числа
сообщений** в канале тик→соединение (конфиг, **[гипотеза: значение]**):
каждое сообщение мелкое и фиксированной формы, счёт байт не нужен.
Чанки через эту очередь не идут: payload берётся из Arc-кэша по
`StreamChunks` и уходит через `batch.rs` (§0), поэтому очередь не
вырастает из-за отдачи чанков.

**Позиции игрока в M4.** Позиция принимается от клиента **без
проверок** — известная дыра (ваниль валидирует движение, мы пока нет),
осознанное решение M4, записано в `DECISIONS.md`. Пока клиент не
подтвердил телепорт (`TeleportAck`), его позиции **игнорируются**.

Что переиспользуется без переделки: `Loader`/`ChunkSource` (мир читается
вне тика), `batch.rs` (пейсинг порций — готовое правило),
`send_radius`/`WorldInfo` (окно уже ограничено min(клиент, сервер)),
keep-alive внутри соединения (не тик), `OnceLock`-кэш payload.

**Доставлено (M4.1/M4.2).** Игровой поток и тик 20 TPS реализованы в
M4.1 (см. `PROGRESS.md`), разбор и применение позиции — в M4.2:

## 1. Регион и планировщик (абстракция закладывается в M4.1 при одном
## регионе; M4.3 расширяет ядро до пула потоков)

- **M4.1 — абстракция есть, регион один.** Игровой поток содержит
  `Region { id, чанковая
  область, ids игроков, очередь входящих }`. Тик = `Region::tick(now)`
  → результат: обновление позиций, пересчёт окон, выдача исходящих
  сообщений. Планировщик в M4.1 тривиален (прогоняет единственного
  региона), но интерфейс сразу «прогоняет N регионов по одному тику» —
  на втором регионе код планировщика не меняется.
- **Как добавляется второй регион:** регион = квадрат чанков (сторона
  **[гипотеза]** 64 чанка, кратность проверит бенч). Карта
  `chunk → region_id`; игрок принадлежит региону своего чанка.
  Разбиение чанков статично (кэш мира заранее размечен по region_id при
  старте).
- **Граница:** движение, пересекающее границу, не применяется на середине
  тика: сообщение `Move` ставится в очередь региона-владельца, а переход
  `region A → region B` применяется в **конце** тика как отдельное
  событие `Transfer { player }` (A → B каналом планировщика). Порядок
  событий внутри тика фиксирован кортежем `(tick, region_id, seq)`
  — детерминизм воспроизводим при одном наборе входящих; реплей-тест
  прогоняет одну запись дважды и сверяет байты исходящих
  **[гипотеза: формула порядка — наша, трейса с двумя регионами нет]**.
- Без новых `Mutex` в горячем пути: регион и есть владелец данных;
  межрегионовые связи — только каналы (правило AGENTS/DECISIONS).

### Многопоточное ядро (как оно устроено)

- **Владелец потоков — игровой планировщик** (новый `std::thread`-пул
  внутри сервера, не tokio): он владеет информацией о регионах, ждёт
  50 мс по абсолютному дедлайну (§3) и раздаёт работы. Пул = `K`
  рабочих потоков, по умолчанию `K = логические ядра − 2`
  (решение D5), настраивается конфигом; каждый поток пула живёт
  вечно и получает регион на такт по каналу.
- **Параллельный тик:** в начале такта планировщик раздаёт регионы
  потокам пула, каждый поток тикает свой `Region::tick` **параллельно**
  с другими. Регион — единственный владелец своих данных, никаких
  `Mutex` (правило AGENTS).
- **Барьер в конце тика:** потоки встречаются на барьере; когда все
  регионы дотикали, планировщик в **том же такте** применяет
  `Transfer`-события (переходы игроков между регионами), затем
  публикует исходящие сообщения и завершает такт. Transfer применяются
  только после того, как все регионы успели к барьеру — это и есть
  правило порядка «сначала параллельная фаза, потом разбор границ».
- **Что делает tokio:** сеть (чтение/запись фреймов, keep-alive,
  пул `net::loader` для диска) — как и сейчас, отдельными задачами
  в runtime. **Что делает пул:** только игровой тик регионов и
  применение Transfer. Tokio и пул не трогают одни и те же данные:
  связь только через каналы (§0).
- Настройки пула (`K`, `K=0` = «всё в одном потоке, пул не создаётся»)
  — параметры конфига **[гипотеза: значения только D5, фактический
  профиль даст M4.6]**.

### Что даёт параллелизм (честно)

Регионный параллелизм ускоряет тик **только при разбросанных по
регионам игроках**: на реальных шаблонах (v2 27×27, цель v3 ~61×61 при
стороне региона 64 — риск б, §7) весь шаблон лежит в одном регионе, и
параллелизма нет вовсе. На синтетике M4.3 проверяет **механизм**
(раздача работ, барьер, Transfer), а **не скорость настоящей игры**.
Реальный выигрыш многоядерности ближайшего времени — не в тике, а в
**загрузке и кодировании чанков** (диск и сеть, уже сейчас вне тика:
`net::loader`, `batch.rs`).

### Реплей и детерминизм (формат записи)

Без записи входящих реплей невозможен, поэтому с форматом реплея
определяемся в M4.1, а не потом:

**Источники недетерминизма и что подаётся записью как входные
данные.** Тик зависит от: (1) времени (`Instant` в теле тика) — тик
фиксирует своё «сейчас» = `start + tick·50ms` и пишет это значение;
(2) случайных значений (id keep-alive) — порождающая сторона
записывает значение в журнал; (3) UUID игрока — фиксируется в строке
`join` такта; (4) порядка сообщений между задачами — назначается
счётчиком `seq` в момент применения события (уже в формате строки).

- Лог-файл (один на прогон, JSONL — по строке на событие), каждая
  строка: `{ "tick": <номер такта применения>, "seq": <порядок внутри
  такта>, "region": <id> | null, "src": <id соединения>, "kind":
  "join" | "move" | "teleport_ack" | "quit" | "transfer" | ...,
  "payload": { ... } }`.
- Ключевой момент: **номер тика, в котором сообщение ПРИМЕНАЕТСЯ**, а
  не момент чтения с сокета: вставка строки производится тиком в
  момент применения (значения полей фиксируются там же). Тогда сеть
  можно выключить из уравнения и реплей = последовательное применение
  журнала при одном и том же состоянии мира.
- Исходящие пакеты при записи не хранятся (это результат), при реплее
  они пересчитываются и сравниваются байт-в-байт со снятым эталоном —
  тест M4.3. Формат строки — проектный, утверждается при M4.1
  **[гипотеза: JSONL и состав полей — наше решение, формат не
  выверен]**.

### Реализовано в M4.3 часть B (10.11.2026)

- **Сетка регионов — параметр конфига.** `net::game::grid::RegionGrid`
  режет мир на квадраты по `region_side` чанков (деление с округлением
  вниз, тайл упакован в один `i32`); `region_side = 0` (default) —
  **разбиения нет**: весь мир — регион 0, поведение до M4.3, поэтому
  живой сервер при дефолте не меняется. Сторону решает бенчмарк M4.6 (D3).
- **Владелец игрока.** Игрок принадлежит региону своего чанка;
  планировщик держит индекс `player_id → region_id` и по нему
  маршрутизирует `Join`/`TeleportAck`/`Quit`/move. `Quit`/`TeleportAck`
  до `Transfer` уходят в старый регион, после — в новый.
- **Transfer после барьера.** Движение, пересекающее границу,
  применяется **в регионе-источнике в этом же такте**; регион лишь
  возвращает `Transfer { player, from, to, seq }`. Планировщик применяет
  все `Transfer` **после барьера** в порядке `(from, seq)` (тай-брейк —
  `player_id`), перенося `Player` целиком по владению; новый регион
  тикает его со следующего такта.
- **Детерминизм.** Игроки региона — `BTreeMap<PlayerId, …>` (обход строго
  по возрастанию id); у каждого события такта свой `seq`; строка реплея
  `kind="transfer"`, payload `{player, from, to}`; строки
  `join`/`move`/`teleport_ack`/`quit` не менялись.
- **«Исходящее» в M4.3 — результаты такта, а не пакеты.** Настоящих
  исходящих пакетов у тика ещё нет (стриминг `StreamChunks` — M4.4),
  поэтому канонический «исходящий транскрипт» = результаты такта
  (применённые позиции, кики, `Transfer`) в порядке `(tick, region, seq)`
  (`TickOutcome::transcript`). Сверка настоящих исходящих пакетов
  байт-в-байт появится в M4.4; тесты M4.3 сверяют транскрипт.

## 2. Кэш чанков: неизменяемое и изменяемое

- Уже есть: `TemplateWorld.ready` — `OnceLock<Arc<ReadyChunks>>` (M4.4 A),
  неизменяемые wire-payload, каждый вход клонирует только указатель.
  **Индекс** `(chunk_x, chunk_z) → позиция в батче` построен (M4.4 A, §4):
  один раз при сборке батча, внутри `ReadyChunks`; окно стриминга
  собирается резолвом координат через индекс, O(радиус), без перебора 729.
- Изменяемое состояние мира (позиции игроков, тики, позднее — блоки) живёт
  только в игровом потоке и передаётся перемещением или через каналы.
  Никакого `Arc<Mutex<Vec<Payload>>>`: при изменениях мира, вносиных
  позже (генерация M6), новая payload строится и попадёт в кэш заменой
  указателя Arc (новая версия), старые клиенты держат старую
  **[гипотеза: атомарная замена ещё не проектировалась под запись]**.
- Связь: тик читает из кэша (Arc, только загрузка), состояние игроков
  решает, *какие* payload отправлять; отправка как и сейчас —
  на той же задаче соединения через `batch.rs`.

## 3. Тик 20 TPS на Windows: ожидание, дрейф, jitter

Замер (09.11.2026, 1000 тактов × 50 мс, release, `tools/tickbench` — отдельный прогон вне workspace `target/tickbench`; два подряд прогона, полный вывод в `docs/TICK-MEASURE.md`):

| сценарий | способ ожидания | дрейф за 1000 тиков | jitter p50 / p99 / p99.9 / max |
|---|---|---|---|
| idle | `std::thread::sleep` до абсолютного дедлайна `start + i·50ms` | **0 мс** (оба прогона) | 0.3–0.5 / **1.0–2.7** / 2.0–12.4 / 5.0–14.7 мс |
| idle | гибрид (sleep до дедлайна −2 мс, затем spin) | **0 мс** (оба прогона) | 0 / 0.01–0.06 / 0.3–0.7 / 0.8–2.6 мс |
| idle | `tokio::time::interval` (текущий keep-alive) | **+2 … +4 мс** | 0–7 / 3.5–14.4 / 3.9–14.8 / 4.2–14.9 мс |
| load | `std::thread::sleep` до абсолютного дедлайна | +15 … +25 мс | 14–21 / 227–1661 / 368–2111 / 418–2161 мс |
| load | гибрид | +28 … +33 мс | 32–35 / 722–1263 / 1107–1500 / 1157–1513 мс |
| load | `tokio::time::interval` | **−31 … +290 мс** | 0–25 / 363–807 / 562–936 / 612–939 мс |

Вывод: игровой поток ждёт по абсолютному дедлайну (`deadline = start +
tick·50ms`, `sleep(deadline - now)`) — дрейф не копится, p99 ≈ 1 мс в
idle; единичные выбросы до ~15 мс — планировщик Windows **[гипотеза:
системный таймер с шагом ≈ 1 мс, подтверждено зондом: `sleep(1 мс)`
медиана ~1–2 мс]**.

Сценарий **«под нагрузкой» нерепрезентативен**: паузы до 2 с,
разброс p99 между прогонами в 7 раз (227 vs 1661 мс) — в выборе
способа ожидания он **не участвует** (см. выше: доминирует нехватка CPU,
а не выбор способа).

`tokio::interval` для тика не берём — дрейф нестабилен (−9/+2/+4/+290 мс
в прошлых прогонах, здесь −31 … +290 мс, median 7–24 мс даже в idle).
**Причина отрицательного дрейфа не объяснена** (ранее записывалось как
«ошибка квантования sleep_until» — отозвано). Проверенная гипотеза базовой
линии: первый `tokio::interval`-тик срабатывает сразу, поэтому 1000
тиков в худшем случае занимают 999 периодов и дрейф ≈ −50 мс. Проверено
по `tools/tickbench` (`run_tokio_interval`): `base` ставится **после**
немедленного первого тика, цикл ждёт 1000 дальше идущих тиков с
дедлайнами `base + i·50ms` — ошибки 999 периодов в замере нет,
исправлять нечего; дрейф остаётся необъяснённым **[гипотеза: причина
локальна для одной машины, не идентифицирована]**.

Гибрид (sleep + spin-хвост) даёт median 0, но под нагрузкой дрейф +28…
+33 мс и p99 722–1263 мс — хуже deadline-sleep по дрейфу, преимущества
не показывает. Короткий spin-хвост добавляется **только если M4.6 покажет,
что выбросы таймера влияют на TPS** **[гипотеза]**.

### Перегруженный тик (не уложился в 50 мс)

Не догоняем пачкой тиков: следующие дедлайны **не** схлопываем в момент
завершения пропущенного — догон стравил бы лавину пропущенных тактов.
Длительность каждого тика логируется (`tracing`, медленные тики —
отдельным уровнем). Если отставание дедлайна превысило **N тиков** —
дедлайн однократно сбрасывается на «сейчас + 50 мс» **[гипотеза: N и
точка сброса — величины, решим по бенчмарку M4.6]**. Метрика
«длительность тика» (p50/p99/max) входит в критерии M4.1 и M4.6.

Тест M4.1: 1000 тактов подряд с порогом «дрейф < 5 мс, p99 jitter < 20 мс» в сценарии idle.

**Реализовано (M4.3 A1 / часть B, 10.11.2026).** В коде сейчас —**
**ограниченный догон.** Тик отстал **меньше** чем на
`period · reset_after = 5·50 = 250 мс` — `sleep_until` возвращается сразу
и пропущенные дедлайны отрабатываются **подряд, без пауз, не
пропускаются**; это расходится с «не догонять пачкой» вплоть до порога.
Только отставание **больше** 250 мс сбрасывает дедлайн один раз на
«сейчас + 50 мс». Порог и точная политика — **M4.6**; на лёгком такте
(наш случай) догон безвреден.

## 4. Стриминг чанков при движении

- Окно: `R = min(client view_distance, server view_distance)` —
  `send_radius` считает её на входе (п.4 A2); это **наше** число
  (self_session при R=8 отдаёт 289 = 17×17), не измерение ванили.
- **Форма окна ванили (измерено `analyze.py shape`, П2/П4/П5).** Загрузка
  после джоина — **23×23 квадрат со срезанными углами** (полуширина 11,
  всего **473** чанка при `view_distance=10`). Число чанков в ряду по |dx|
  (и то же по |dz|): 0..6 → 23, 7 → 21, 8 → 19, 9 → 19, 10 → 15, 11 → 13;
  итого 473 = 529 − 56. Набор совпадает с кругом `|dx|²+|dz|² ≤ 162`;
  правило углов и полуширина 11 = R+1 одним R не доказаны — **[гипотеза]**.
  Значит окно — **не** `±10` (441), а 473; поэтому «внутри окна r=10» из
  критерия M4.0 — про генерацию, а окно пакетов шире на 1.
- **Область применимости формулы — уточнена в M4.4 B.** Форма снята при
  четырёх `view_distance` (ЧАСТЬ 0, таблица ниже): квадрат полуширины `R+1`
  со срезанными по кругу `dx²+dz² ≤ K(R)` углами подтверждён **по
  отдельности** для R = 6/8/10/12. Формула `K(R)` найдена в M4.4 B (ниже) и
  применяется для `R` в `6..=12`; вне диапазона в коде остаётся квадрат
  `(2R+1)²` — **[гипотеза, не проверено]**.
- **Наш сервер собирает окно из трейса при R=10 (M4.4 A, ЧАСТИ 1/2,
  10.11.2026).** Было `21×21 = 441` (`send_radius`, R=10) — расхождение с
  ванилью (473); теперь `net::chunks::window` отдаёт 473 при R=10 и
  квадрат `(2R+1)2` при всех прочих R. Реализация и проверка — ниже.
- **Сдвиг окна (измерено).** При сдвиге центра на 1 чанк приходит ровно то,
  что забывается (ведущий край меняется на ведомый), loaded остаётся 473.
  П4 (+x): приходит 23 = ведущий край (ряды dx=11:|dz|≤6, 10:±7, 9:±8..9,

  ведущие края +x и +z (23+23−9 уже бывших). Отсюда 23/37, а не 21/41.
- **Первый сдвиг П4 — это джоин.** До него отдано 313 чанков (`t=1278..6432`),

  ещё не заполнилось, нечего было выгружать. «473» — это полное окно, а

- Данные по трейсу: трейсы ходьбы **есть** — `window-p2/p3.jsonl` (раунд 5,
  v2) и `window-p4/p5.jsonl` (раунд 5, v3). Наблюдено: `set_chunk_cache_center`
  двигается вслед за текущим чанком бота (центр = чанк бота, 4/4/8/6 точек
  на П2/П3/П4/П5); при пересечении границы чанка сервер шлёт
  `forget_level_chunk` на чанки, вышедшие из окна, и догружает освободившиеся
  батчем. П4: (6,−2)→(13,−2) по x; П5: (6,−2)→(11,3) по диагонали.
- Порядок и пейсинг догрузки: `batch.rs` (первая порция 9, ack →
  `ceil(rate)` чанков за 50 мс) — на догрузке применяется то же правило
  **[гипотеза: на джоине подтверждено; размеры порций на ходьбе измерены
  (медиана 4 чанка), но правило `ceil(rate)` по трейсу не выведено]**.
- Выгрузка `forget_level_chunk` по проводу: **packed `ChunkPos`** — один
  big-endian `i64` (payload 8 Б), **z в старшем слове, x в младшем**, то
  есть на проводе сначала идёт z. Не VarInt и не 3-байтная packed-позиция
  блока. Уточнено в ШАГ 4 по трейсу: если первое слово читать как x, забытая
  колонка не совпадает с `window(old) − window(new)`; если как z —
  совпадает байт в байт (23/23 на каждом сдвиге П4). Раунды 4–5 верно
  фиксировали размер (8 Б = два i32), но не порядок слов.
- Проверка стриминга на дистанции 100+ чанков (критерий M4.4)
  разрешена на шаблоне v3 **или на синтетическом провайдере** (параграф
  5): на v2 сплошная полоса всего 27×27 — короткий заезд, не далее.
- **Видимость игроков (M4.5) идёт в том же тике, что и стриминг чанков, но
  окна не меняет.** Проход видимости и сборка entity-пакетов — отдельные
  фазы тика (замер — Шаг 3.5, `docs/BENCH-M4.md` §9): на uniform P=200 p99
  после оптимизации **2.81–2.98 мс ≤ 5 мс**; тик-цена (а)+(г) = 0.39 мс p50.
  Разбиение чанков на регионы и окно `±R` от позиции — те же, что при
  стриминге; видимость считается по позициям игроков и от границы регионов
  не зависит (§6, Шаг 4 (а)/(б)). Детали пакетов — §6, Шаг 1 и Шаг 3.

### Форма окна на входе — измерено на четырёх радиусах (ЧАСТЬ 0, M4.4 A, 10.11.2026)

Прогон `crates/parity/tests/join_window.rs` (`analyze.py shape-join`): бот
входит на свежую копию v2 и стоит без движения; `view-distance` и

срабатывал). Центр всегда (6,−2), одна смена центра, первая порция всегда
**9** чанков (3×3). Трейсы `C:\MineRust-data\traces\join-window-r*.jsonl`.

| R | чанков | полуширина h | круг K | статус |
|---|--------|--------------|--------|--------|
| 6 | 213 | 7 | 74 | по трейсу |
| 8 | 329 | 9 | 113 | по трейсу |

- Все четыре набора **симметричны** относительно (6,−2) (зеркало по x, по

- **Формула `K(R)` — найдена (M4.4 B, 10.11.2026).** При полуширине
  `h = R+1` срез углов `dx²+dz² ≤ K(R)` есть `K(R) = floor((h + √3)²)`.

  `(h+√3)² = h² + 3 + √(12·h²)`, то есть `K(h) = h² + 3 + isqrt(12·h²)`.
  Это **[гипотеза]** (по четырём точкам, вне 6..12 не проверена), включена
  для `R ∈ 6..=12`; для остальных R остаётся квадрат `(2R+1)²` —
  **[гипотеза, не проверено]** (`DECISIONS.md`).
- **Порядок отправки на входе (R=10).** Первая порция — 9 чанков 3×3 вокруг
  центра, дальше порции мельче; **внутри каждой порции 0 регрессий** по
  `dx²+dz²` (во всех четырёх радиусах), регрессии только на границах порций.
  Первичный ключ `dx²+dz²` подтверждён; порядок чанков с равным `dx²+dz²`
  (вторичный ключ) по трейсу **не установлен** → оставляем текущий
  `(dx²+dz², x, z)`.
- **Проверка чистоты.** Шаблон v2 после прогонов не изменён: `world-template`
  и `world-template-v2` побайтно совпадают (36 файлов, 15 402 135 Б, один
  агрегат SHA-256 `f8ab3f2f…`); прогон копирует шаблон, а не правит его.

### Формула K(R) для R=6..12 (M4.4 B, ШАГ 0, 10.11.2026)

Без новых прогонов ванили (по данным ЧАСТИ 0). Для каждого R — интервал
значений `K`, при которых круг в квадрате `h = R+1` даёт ровно измеренное
множество, и значение формулы `K(R) = floor((h + √3)²)`:

| R | чанков | h | интервал K | K по формуле | попало |
|---|--------|----|-----------|--------------|--------|
| 6 | 213 | 7 | [74, 84] | 76 | да |
| 8 | 329 | 9 | [113, 116] | 115 | да |
| 10 | 473 | 11 | [162, 163] | 162 | да |
| 12 | 637 | 13 | [208, 217] | 217 | да |

Формула попала во **все четыре** интервала → включена для `R ∈ 6..=12`
(целочисленно: `(h+√3)² = h² + 3 + √(12·h²)`, `WINDOW_CUT = 3 = (√3)²`,
побитовый `isqrt`); вне диапазона — квадрат `(2R+1)²`. Статус:
**[гипотеза]** (по четырём точкам, вне `6..12` не проверена). Тесты
`net::chunks`: `the_formula_reproduces_every_measured_radius`
(213/329/473/637), `the_corner_cut_matches_the_measured_circles`
(76/115/162/217), `the_integer_square_root_floors_the_real_one`,
`every_untraced_radius_is_the_full_square`.

### Порядок пакетов на сдвиге центра (M4.4 B, ШАГ 1, 10.11.2026)

По ванильным трейсам `window-p4/p5.jsonl` (v3, ходьба). На переходе
`центр old → new` (`analyze.py`, агрегаты) события идут строго:
**`set_chunk_cache_center`(new) → все `forget_level_chunk` →
`chunk_batch_start` → `level_chunk_with_light` → `chunk_batch_finished`**
(проверено на всех устойчивых сдвигах обоих трейсов). `set_chunk_cache_center`
объявляет **новый** центр и приходит **до** забытий. Забытия идут одним
непрерывным блоком (без посторонних пакетов между ними).

- **Порядок forget внутри сдвига — однозначно `(x, z)` по возрастанию**
  (абсолютные координаты; то же, что возрастание `(dx, dz)` от старого
  центра). Совпал с трейсом **6/6** (П4) и **5/5** (П5); `(z, x)`,
  `(x desc, z)`, по расстоянию от старого центра (возр./убыв.) — **не**
  совпали. Это **решено по трейсу**.
- Множество забытых = `window(old) − window(new)` (23 при сдвиге по x, 37 по
  диагонали) — совпало по координатам на всех устойчивых сдвигах.
- Первый переход (во время входа) не считается: окно ещё не заполнено —
  забытий 0 (П4) / 30 из 37 (П5).
- **Кодек `forget_level_chunk` (M4.4 B).** id 38 (`packets.json`), payload —
  **packed `ChunkPos`**: один big-endian `i64` (8 Б), **z в старшем слове, x
  в младшем** (на проводе z первым). Тест
  `forget_level_chunk_matches_the_traced_payloads` на реальных payload из П4
  (seq 16000 = `(x,z)=(-4,-8)`, seq 16022 = `(1,9)`), отрицательные
  координаты round-trip. Порядок слов исправлен в ШАГ 4 (см. выше); раньше
  первым словом ошибочно считался x. `protocol` больше не менялся.

### Сторона тика: событие сдвига окна (M4.4 B, ШАГ 2, 10.11.2026)

- **`Player.window_center`** (чанк) — центр кэша клиента. На входе = чанк
  спавна; меняется, когда применённое движение переводит игрока в другой
  чанк `(floor(x/16), floor(z/16))` (флоринг как у `region_of_position`;
  `x = −0.5 → чанк −1`). Обновляется только после `TeleportAck` (движение до
  него игнорируется, как в M4.2).
- **`Region::tick` эмитит `StreamChunks { region, player, seq, center, add,
  remove }`** в `TickOutcome.streams`, когда центр меняется. `add =
  window(new) − window(old)` в порядке отправки нового центра (`(dx2+dz2, x,
  z)`), `remove = window(old) − window(new)` по возрастанию `(x, z)` (порядок
  forget из ШАГ 1). Оба — чистая функция `net::chunks::window_difference`.
  Несколько сдвигов чанка за такт дают **одно** событие «старый центр →
  финальный» (сравнение с центром на начало такта, не по шагам).
- **`seq` общий** для move/transfer/stream внутри региона; строка транскрипта
  `kind="stream"` с `center`, `add`, `remove`; порядок транскрипта
  `(tick, region, seq)`. **Реплей-журнал не расширяется**: стриминг — это
  транспортное состояние, не игровое (в журнал `stream` не пишется).
- **Доставка.** Планировщик получил `Scheduler::deliver(id, message)`: маршрут
  по `player_id → region_id` **после** переносов такта (игрок, пересёкший
  границу, получает событие в новом регионе), `try_send` без блокировки,
  переполнение очереди = кик (та же политика, что у прочих сообщений
  тик→соединение). Игровой цикл (`game/mod.rs::deliver_streams`) шлёт
  `ServerMessage::StreamChunks { center, add, remove }` соединению; сторона
  соединения (set_cache_center/forget/догрузка) — ШАГ 3.
- **Проверка (тесты).** (а) сдвиг x на чанк → 23/23, диагональ → 37/37;
  (б) движение внутри чанка → нет событий; `x=−0.5` → центр `(−1,0)`;
  (в) длинное движение через границу региона + чанка → ровно одно событие с
  верным центром и доставкой в регион-получатель; (г) транскрипт совпадает
  при K=0/1/4/8 и при повторе; (д) воспроизведение журнала даёт те же
  `stream`-события (из `move`, журнал без `stream`). Это **решено тестом**.

### Сторона соединения: очередь-сессия и сдвиг окна (M4.4 B, ШАГ 3, 10.11.2026)

- **`PendingBatch` стал очередью на всю сессию**, а не разовым джоином.
  Держит `queue: VecDeque<(x,z)>` (координаты к отправке, в порядке
  отправки), `sent: BTreeSet<(x,z)>` (уже на проводе), `center`, `radius`,
  `not_cached`, `opened`. `Stage::Parked` — очередь пуста, arm цикла молчит
  (`std::future::pending`), таймер не заводится. `send_next` при пустой
  очереди либо пишет один пустой джоин-батч (если `!opened`), либо
  паркуется и возвращает `Ok(true)`; цикл **больше не бросает** отправителя
  после первого батча.
- **`PendingBatch::move_window(center, add, remove) -> Vec<(x,z)>`** — один
  сдвиг: центр ← `center`; каждый `remove`: если ещё в `queue` — тихо
  убрать (клиент его не видел), если в `sent` — вернуть на
  `forget_level_chunk` и убрать из `sent`, иначе игнор; каждый `add`: если
  не в `sent`/`queue` и есть в ready-индексе — в хвост `queue`, иначе
  `not_cached++` (info). Возврат — забытия в порядке `remove` (по
  возрастанию `(x,z)`, из ШАГ 1).
- **Порядок на проводе** — `batch::write_window_move`: сначала
  `set_chunk_cache_center`(new), затем все `forget_level_chunk` (порядок
  `move_window`), затем новые чанки ждут батч-arm. Это ровно порядок из
  ШАГ 1 (решено по трейсу).
- **Инвариант** (M4.4 B): после каждого `StreamChunks`/`move_window`
  `sent ∪ queue` не содержит ни одного чанка вне `window(center)` —
  `debug_assert!` в `move_window` (`within_window`, debug-сборки) и явные
  проверки в тесте. Это **решено тестом**.
- **Центр на стороне соединения** — `stream_center` (стартует чанком
  спавна); обновляется первым делом на `StreamChunks`. Если мир ещё не
  прочитан (`pending == None`), окно входа строится уже по текущему
  `stream_center`, поэтому чанк вне нового окна не уходит.
- **`batch.rs` от ШАГ 3 (сверх ШАГ 2):** очередь вместо `order/next`,
  `sent`, `center/radius/not_cached/opened`, `Stage::Parked`,
  `move_window`, `within_window`, `queued`, `write_window_move`. Логика
  первого флаша/полки/хвоста (`FIRST_FLUSH`, `PACE_WAIT`, `TICK`) **не
  менялась**: джоин ведёт себя как раньше.
- **Проверка (тесты).** (а) «быстрее, чем приходят порции»: пять сдвигов
  при pace=2, между ними по одной маленькой порции; после каждого сдвига
  инвариант держится, каждый forget — ранее отправленный чанк, остаток
  очереди вне окна не остаётся, полностью слитая сессия = `window(final) ∩
  ready`; (б) провод: `set_chunk_cache_center`, затем forget по
  возрастанию `(x,z)` ровно для ушедших отправленных, догрузка — только
  новые чанки, без повторов. Джоин-тесты (20 чанков, `[9,8,3]`) не
  изменились. Это **решено тестом**.

**A2 — пул потоков и барьер (механизм; один регион).**

1. Пул: новый `net::game::pool` — `K` `std::thread` («minecraft-region-i»),
   регион **передаётся по владению** (mpsc), воркер тикает и возвращает;
   новых `Mutex`/`RwLock` в горячем пути нет. Остановка вместе с игровым
   потоком: `Drop for Pool` закрывает каналы и ждёт воркеров ≤2 с
   (`join`); при таймауте — `warn` и отсоединение.
2. Раздача и барьер — `Scheduler::tick_pooled`: `K` регионов уходят по
   кругу, планировщик собирает ровно столько результатов, сколько
   отправил; merge сортирует по `region_id` (не по порядку завершения).
   При **≤1** регионе — `tick_inline` (M4.1-путь), поэтому сервер
   ведёт себя как раньше. `Region::tick` обходит игроков в порядке id
   (детерминизм merge; порядок `HashMap` им не был).
3. Параметр: `GameConfig.workers` (default `0` — пул не создаётся);
   `ServerConfig.workers` в `server.toml` (default `ядра−2`, минимум 1;
   `0` выключает пул); `net::serve_with(GameConfig, ...)` — новый вход,
   `net::serve` делегирует с `GameConfig::default()`, поэтому parity и
   in-process серверы не изменились; `server::run` передаёт
   `config.workers`.
4. Тесты (`net`, `game::tests`): (а) K=0/1/4 при 8 регионах дают равный
   объединённый `TickOutcome`; (б) merge не зависит от порядка
   завершения (искусственная задержка 50 мс в регионе 0); (в) пул
   останавливается < 2 с; (г) 1000 пустых тактов при K=4 на 4 регионах:
   drift 0.597 мс, jitter p50 0.487 / p99 1.030 / max 1.479 мс; тик в
   игровом цикле с пулом (5 тактов) проходит и пул корректно
   присоединяется.
5. Inline против передачи на одном регионе (20 000 тактов, release):
   inline p50 0.100 / p99 0.100 мкс, передача p50 0.700 / p99 1.900 мкс.
   Решение — inline для ≤1 региона (`DECISIONS.md`, **[гипотеза]** до
   M4.6: разница мала на фоне периода 50 мс).

### M4.3 часть B — план (выполнено, 10.11.2026)

1. **B1 — карта регионов и `Transfer`.** `net::game::grid::RegionGrid` режет
   мир на квадраты по `region_side` чанков; `GameConfig.region_side` /
   `ServerConfig.region_side` (default **0 = нет разбиения**, весь мир =
   регион 0). `Region.players` — `BTreeMap<PlayerId, Player>`;

   индекс владельца в `Scheduler`; маршрутизация `Join`/`TeleportAck`/
   `Quit`; применение `Transfer` **после барьера** в порядке `(from, seq)`;
   `TickOutcome::transcript`; строка реплея `kind="transfer"`
   `{player, from, to}`. Живой сервер при `region_side=0` не изменился.
2. **B2 — сценарии (без сокетов, in-process, сторона 2 чанка, K=0/1/4).**
   (а) переход границы: движение применяется в источнике, `Transfer` в том
   же такте, позиция непрерывна, дальше тикает новый регион; (б) четыре
   игрока пересекают в одном такте в обе стороны и в разные регионы —
   порядок `(from, seq)`, транскрипт одинаков при K=0/1/4; (в) `Quit`
   маршрутизируется к текущему владельцу (до `Transfer` — старый, после —
   новый); (г) неподтверждённый игрок не переносится (его движения
   игнорируются), подтверждение переживает `Transfer`; (д) пять игроков ×
   десять тактов — на каждом такте каждый игрок ровно в одном регионе,
   сумма = живые (без потерь и дублей).
3. **B3 — канонический «исходящий» транскрипт и реплей-тесты.**

### Риски

1. **(а) Статическое разбиение регионов против окна видимости,
   пересекающего границу региона.** Разбиение чанков на регионы статично
   (§1), а окно игрока — квадрат ±R, который спокойно заходит за границу
   обоих регионов. Для M4 (позиции) это решается `Transfer`, но для
   **блоков в M5** нужны обновления состояния мира между регионами;
   Folia для таких случаев объединяет регионы **динамически**, а наша
   схема статическая. Расхождение договорённостей: решать к M5, в M4 не
   трогаем **[гипотеза: объём межрегионовых обновлений для M5 пока не
   оценён]**.
2. **(б) Сторона региона 64 чанка — весь шаблон в одном регионе.**
   Готовая область v2 (27×27) и даже цель v3 (~61×61) укладываются в
   квадрат со стороной 64, т.е. ложатся в **один** регион → на реальном
   шаблоне второго региона просто нет: параллельный тик и `Transfer`
   проверяются только на **синтетике** (M4.3 берёт синтетические чанки)
   **[гипотеза: совпадение области с тайлами зависит от начала сетки
   регионов — привязку проверим на практике]**.
