Дата 09.11.2026, статус: проект, ждёт «дизайн принят». Всё
неподтверждённое помечено **[гипотеза]**; имена в разделе 0 проверены

## 0. Как устроено сейчас (основа изменений)

- `net::serve` принимает соединения и на каждое спавнит собственную
  tokio-задачу → `handle_connection` → `play_state`. В `play_state`:
  join-последовательность (`join::send_join`), фоновое чтение фреймов в
  mpsc-канал, `select!` с ветками keep-alive / ответа загрузчика /
  отправки батча / входящих фреймов; пакеты движения распознаются, но
  пишутся `trace!("movement received, ignored")` — **позиции игрока не
  существуют**.
- Мир: `server::build_world` создаёт `TemplateWorld` (кэш
  `ready: OnceLock<Arc<Vec<LevelChunkWithLight>>>`) и пул `net::loader`
  (2 именованных потока, ограниченные очереди по 4, ответ через
  oneshot), `serve` раздаёт `Loader` клонами. `play_state` читает батч
  один раз на вход и больше со взаимодействия с миром не имеет.
- Отправка чанков — `play/batch.rs`: `PendingBatch`, состояния
  First → AwaitPace(1 с) → Pace(50 мс), первая порция 9, по
  `chunk_batch_received` — `ceil(rate)` за тик (п.5 A2, `6d113a8`).
- Игрового потока и тика **нет вовсе**: время обслуживается только
  интервалами внутри отдельных задач (keep-alive 15 с, тика-пути нет).

**Что должно измениться.** Состояние игроков и мира переезжает в
один игровой поток (тик), соединение становится тонким кодеком:

```
 TcpStream                      игровой поток (20 TPS)
 ┌──────────────┐  mpsc(N)     ┌──────────────────────────────┐
 │ play_state:  │  Move{pos}:  │ Registry игроков (owner:      │
 │  decode/encode├────────────►│  HashMap<id, Player>),        │
 │  keep-alive  │◄────────────┤  окна стриминга, кэш мира,    │
 │  batch.rs    │  Outbound:   │  очередь сообщений регионов   │
 └──────────────┘  Packet(..)  └──────────────────────────────┘
        ▲ oneshot: join/quit                    │
        └──────── load payload (существующий net::loader)
```

Сообщения (bounded-каналы, размер задаётся: переполнение = backpressure
на приёме, а не блокировка тика — **[гипотеза]**, точный размер даст
бенч):

- вверх: `Join { id, name, view_distance, pos }`,
  `TeleportAck { id, teleport_id }`, `Quit { id }` — надёжные сообщения;
  `Move { id, pos, yaw, pitch, on_ground }` — не сообщение в очередь, а
  слот «последняя позиция игрока» в его состоянии (клиент шлёт позицию
  20 раз в секунду, тику нужна последняя, старая перезаписывается);
- вниз: `StreamChunks { id, add, remove }` — тик решает, какие чанки
  (payload, `Arc`) добавить в окно игрока и какие убрать; соединение
  берёт `Arc`-payload из кэша и шлёт их через существующий `batch.rs`
  (пейсинг и порядок — §4). И `Send { id, packet }` — реактивные
  исходящие вне тика (телепорт-подтверждение, сообщения об ошибке
  чтения).

**Политика медленного клиента (явно).** Исходящая очередь одного
клиента ограничена (`try_send`-семантика, размер задаётся конфигом).
Если очередь переполнилась — **тик не блокируется и не ждёт**: клиенту
уходит kick с причиной «send queue overflow» и разрыв. Это решение,
а не побочный эффект: одна медленная TCP-задача не может остановить
весь мир.

**Надёжный путь (взамен «узкого пути с приоритетом»).** `Join`, `Quit`
и `TeleportAck` соединение отправляет тику через `send().await`:
тормозит только эта сетевая задача, сообщение не теряется. Тик читает
входящее через `try_recv` и никогда не ждёт.

**Переполнение исходящей очереди клиента** — это превышение **числа
сообщений** в канале тик→соединение (конфиг, **[гипотеза: значение]**):
каждое сообщение мелкое и фиксированной формы, счёт байт не нужен.
Чанки через эту очередь не идут: payload берётся из Arc-кэша по
`StreamChunks` и уходит через `batch.rs` (§0), поэтому очередь не
вырастает из-за отдачи чанков.

**Позиции игрока в M4.** Позиция принимается от клиента **без
проверок** — известная дыра (ваниль валидирует движение, мы пока нет),
осознанное решение M4, записано в `DECISIONS.md`. Пока клиент не
подтвердил телепорт (`TeleportAck`), его позиции **игнорируются**.

Что переиспользуется без переделки: `Loader`/`ChunkSource` (мир читается
вне тика), `batch.rs` (пейсинг порций — готовое правило),
`send_radius`/`WorldInfo` (окно уже ограничено min(клиент, сервер)),
keep-alive внутри соединения (не тик), `OnceLock`-кэш payload.

## 1. Регион и планировщик (абстракция закладывается в M4.1 при одном
## регионе; M4.3 расширяет ядро до пула потоков)

- **M4.1 — абстракция есть, регион один.** Игровой поток содержит
  `Region { id, чанковая
  область, ids игроков, очередь входящих }`. Тик = `Region::tick(now)`
  → результат: обновление позиций, пересчёт окон, выдача исходящих
  сообщений. Планировщик в M4.1 тривиален (прогоняет единственного
  региона), но интерфейс сразу «прогоняет N регионов по одному тику» —
  на втором регионе код планировщика не меняется.
- **Как добавляется второй регион:** регион = квадрат чанков (сторона
  **[гипотеза]** 64 чанка, кратность проверит бенч). Карта
  `chunk → region_id`; игрок принадлежит региону своего чанка.
  Разбиение чанков статично (кэш мира заранее размечен по region_id при
  старте).
- **Граница:** движение, пересекающее границу, не применяется на середине
  тика: сообщение `Move` ставится в очередь региона-владельца, а переход
  `region A → region B` применяется в **конце** тика как отдельное
  событие `Transfer { player }` (A → B каналом планировщика). Порядок
  событий внутри тика фиксирован кортежем `(tick, region_id, seq)`
  — детерминизм воспроизводим при одном наборе входящих; реплей-тест
  прогоняет одну запись дважды и сверяет байты исходящих
  **[гипотеза: формула порядка — наша, трейса с двумя регионами нет]**.
- Без новых `Mutex` в горячем пути: регион и есть владелец данных;
  межрегионовые связи — только каналы (правило AGENTS/DECISIONS).

### Многопоточное ядро (как оно устроено)

- **Владелец потоков — игровой планировщик** (новый `std::thread`-пул
  внутри сервера, не tokio): он владеет информацией о регионах, ждёт
  50 мс по абсолютному дедлайну (§3) и раздаёт работы. Пул = `K`
  рабочих потоков, по умолчанию `K = логические ядра − 2`
  (решение D5), настраивается конфигом; каждый поток пула живёт
  вечно и получает регион на такт по каналу.
- **Параллельный тик:** в начале такта планировщик раздаёт регионы
  потокам пула, каждый поток тикает свой `Region::tick` **параллельно**
  с другими. Регион — единственный владелец своих данных, никаких
  `Mutex` (правило AGENTS).
- **Барьер в конце тика:** потоки встречаются на барьере; когда все
  регионы дотикали, планировщик в **том же такте** применяет
  `Transfer`-события (переходы игроков между регионами), затем
  публикует исходящие сообщения и завершает такт. Transfer применяются
  только после того, как все регионы успели к барьеру — это и есть
  правило порядка «сначала параллельная фаза, потом разбор границ».
- **Что делает tokio:** сеть (чтение/запись фреймов, keep-alive,
  пул `net::loader` для диска) — как и сейчас, отдельными задачами
  в runtime. **Что делает пул:** только игровой тик регионов и
  применение Transfer. Tokio и пул не трогают одни и те же данные:
  связь только через каналы (§0).
- Настройки пула (`K`, `K=0` = «всё в одном потоке, пул не создаётся»)
  — параметры конфига **[гипотеза: значения только D5, фактический
  профиль даст M4.6]**.

### Что даёт параллелизм (честно)

Регионный параллелизм ускоряет тик **только при разбросанных по
регионам игроках**: на реальных шаблонах (v2 27×27, цель v3 ~61×61 при
стороне региона 64 — риск б, §7) весь шаблон лежит в одном регионе, и
параллелизма нет вовсе. На синтетике M4.3 проверяет **механизм**
(раздача работ, барьер, Transfer), а **не скорость настоящей игры**.
Реальный выигрыш многоядерности ближайшего времени — не в тике, а в
**загрузке и кодировании чанков** (диск и сеть, уже сейчас вне тика:
`net::loader`, `batch.rs`).

### Реплей и детерминизм (формат записи)

Без записи входящих реплей невозможен, поэтому с форматом реплея
определяемся в M4.1, а не потом:

**Источники недетерминизма и что подаётся записью как входные
данные.** Тик зависит от: (1) времени (`Instant` в теле тика) — тик
фиксирует своё «сейчас» = `start + tick·50ms` и пишет это значение;
(2) случайных значений (id keep-alive) — порождающая сторона
записывает значение в журнал; (3) UUID игрока — фиксируется в строке
`join` такта; (4) порядка сообщений между задачами — назначается
счётчиком `seq` в момент применения события (уже в формате строки).

- Лог-файл (один на прогон, JSONL — по строке на событие), каждая
  строка: `{ "tick": <номер такта применения>, "seq": <порядок внутри
  такта>, "region": <id> | null, "src": <id соединения>, "kind":
  "join" | "move" | "teleport_ack" | "quit" | "transfer" | ...,
  "payload": { ... } }`.
- Ключевой момент: **номер тика, в котором сообщение ПРИМЕНАЕТСЯ**, а
  не момент чтения с сокета: вставка строки производится тиком в
  момент применения (значения полей фиксируются там же). Тогда сеть
  можно выключить из уравнения и реплей = последовательное применение
  журнала при одном и том же состоянии мира.
- Исходящие пакеты при записи не хранятся (это результат), при реплее
  они пересчитываются и сравниваются байт-в-байт со снятым эталоном —
  тест M4.3. Формат строки — проектный, утверждается при M4.1
  **[гипотеза: JSONL и состав полей — наше решение, формат не
  выверен]**.

## 2. Кэш чанков: неизменяемое и изменяемое

- Уже есть: `TemplateWorld.ready` — `OnceLock<Arc<Vec<...>>>`,
  неизменяемые wire-payload, каждый вход клонирует только указатель.
  M4 добавляет **индекс** `(chunk_x, chunk_z) → позиция в батче` (при
  старте, один раз), чтобы окно стриминга собиралось O(радиус) без
  перебора 729.
- Изменяемое состояние мира (позиции игроков, тики, позднее — блоки) живёт
  только в игровом потоке и передаётся перемещением или через каналы.
  Никакого `Arc<Mutex<Vec<Payload>>>`: при изменениях мира, вносиных
  позже (генерация M6), новая payload строится и попадёт в кэш заменой
  указателя Arc (новая версия), старые клиенты держат старую
  **[гипотеза: атомарная замена ещё не проектировалась под запись]**.
- Связь: тик читает из кэша (Arc, только загрузка), состояние игроков
  решает, *какие* payload отправлять; отправка как и сейчас —
  на той же задаче соединения через `batch.rs`.

## 3. Тик 20 TPS на Windows: ожидание, дрейф, jitter

Замер (09.11.2026, 1000 тактов × 50 мс, release, `tools/tickbench` — отдельный прогон вне workspace `target/tickbench`; два подряд прогона, полный вывод в `docs/TICK-MEASURE.md`):

| сценарий | способ ожидания | дрейф за 1000 тиков | jitter p50 / p99 / p99.9 / max |
|---|---|---|---|
| idle | `std::thread::sleep` до абсолютного дедлайна `start + i·50ms` | **0 мс** (оба прогона) | 0.3–0.5 / **1.0–2.7** / 2.0–12.4 / 5.0–14.7 мс |
| idle | гибрид (sleep до дедлайна −2 мс, затем spin) | **0 мс** (оба прогона) | 0 / 0.01–0.06 / 0.3–0.7 / 0.8–2.6 мс |
| idle | `tokio::time::interval` (текущий keep-alive) | **+2 … +4 мс** | 0–7 / 3.5–14.4 / 3.9–14.8 / 4.2–14.9 мс |
| load | `std::thread::sleep` до абсолютного дедлайна | +15 … +25 мс | 14–21 / 227–1661 / 368–2111 / 418–2161 мс |
| load | гибрид | +28 … +33 мс | 32–35 / 722–1263 / 1107–1500 / 1157–1513 мс |
| load | `tokio::time::interval` | **−31 … +290 мс** | 0–25 / 363–807 / 562–936 / 612–939 мс |

Вывод: игровой поток ждёт по абсолютному дедлайну (`deadline = start +
tick·50ms`, `sleep(deadline - now)`) — дрейф не копится, p99 ≈ 1 мс в
idle; единичные выбросы до ~15 мс — планировщик Windows **[гипотеза:
системный таймер с шагом ≈ 1 мс, подтверждено зондом: `sleep(1 мс)`
медиана ~1–2 мс]**.

Сценарий **«под нагрузкой» нерепрезентативен**: паузы до 2 с,
разброс p99 между прогонами в 7 раз (227 vs 1661 мс) — в выборе
способа ожидания он **не участвует** (см. выше: доминирует нехватка CPU,
а не выбор способа).

`tokio::interval` для тика не берём — дрейф нестабилен (−9/+2/+4/+290 мс
в прошлых прогонах, здесь −31 … +290 мс, median 7–24 мс даже в idle).
**Причина отрицательного дрейфа не объяснена** (ранее записывалось как
«ошибка квантования sleep_until» — отозвано). Проверенная гипотеза базовой
линии: первый `tokio::interval`-тик срабатывает сразу, поэтому 1000
тиков в худшем случае занимают 999 периодов и дрейф ≈ −50 мс. Проверено
по `tools/tickbench` (`run_tokio_interval`): `base` ставится **после**
немедленного первого тика, цикл ждёт 1000 дальше идущих тиков с
дедлайнами `base + i·50ms` — ошибки 999 периодов в замере нет,
исправлять нечего; дрейф остаётся необъяснённым **[гипотеза: причина
локальна для одной машины, не идентифицирована]**.

Гибрид (sleep + spin-хвост) даёт median 0, но под нагрузкой дрейф +28…
+33 мс и p99 722–1263 мс — хуже deadline-sleep по дрейфу, преимущества
не показывает. Короткий spin-хвост добавляется **только если M4.6 покажет,
что выбросы таймера влияют на TPS** **[гипотеза]**.

### Перегруженный тик (не уложился в 50 мс)

Не догоняем пачкой тиков: следующие дедлайны **не** схлопываем в момент
завершения пропущенного — догон стравил бы лавину пропущенных тактов.
Длительность каждого тика логируется (`tracing`, медленные тики —
отдельным уровнем). Если отставание дедлайна превысило **N тиков** —
дедлайн однократно сбрасывается на «сейчас + 50 мс» **[гипотеза: N и
точка сброса — величины, решим по бенчмарку M4.6]**. Метрика
«длительность тика» (p50/p99/max) входит в критерии M4.1 и M4.6.

Тест M4.1: 1000 тактов подряд с порогом «дрейф < 5 мс, p99 jitter < 20 мс» в сценарии idle.

## 4. Стриминг чанков при движении

- Окно: `R = min(client view_distance, server view_distance)` —
  `send_radius` уже считает это на входе (п.4 A2). Окно — чанковый
  квадрат `±R` вокруг текущего чанка игрока **[гипотеза: квадрат
  подтверждён только на джоине — 289 = 17×17 при R=8; форма при ходьбе
  не измерена]**.
- Данные по трейсу: **трейса ходьбы ванили нет ни в одном имеющемся
  файле**: `join-vanilla.v2runB.json`, `live-session.json`,
  `self-session.json` содержат ровно **1** `set_chunk_cache_center` (это
  джоин) и **0** `forget_level_chunk`. Т.е. поведение при ходьбе
  пока это **[гипотеза]**: центр сдвигается, когда игрок уходит на
  ~16+ блоков от текущего центра, чанки вне `±R` выгружаются
  `minecraft:forget_level_chunk`, освободившиеся догружаются батчем.
  Запись трейса ходьбы — задача M4.0 (нужна ваниль и сценарий ходьбы).
- Порядок и пейсинг догрузки уже готовы: `batch.rs` (первая порция 9,
  ack → `ceil(rate)` чанков за 50 мс) — на догрузке применяется то же
  правило **[гипотеза: на джоине подтверждено, на движении не измерено]**.
- Выгрузка `forget_level_chunk` по проводу: три байта packed x/z
  **[гипотеза: раскладку подтвердит трейс M4.0]**.
- Проверка стриминга на дистанции 100+ чанков (критерий M4.4)
  разрешена на шаблоне v3 **или на синтетическом провайдере** (параграф
  5): на v2 сплошная полоса всего 27×27 — короткий заезд, не далее.

## 5. Бенчмарки: `crates/bench`

- Генератор ботов: N клиентов проходят настоящий handshake/login/play
  (клиент bench свой, лёгкий — без трейс-записи, которой живёт
  `parity::join_steps`; **[гипотеза]**), затем шлют move-пакеты по
  своим путям (спираль/линия по регионам).
- **Синтетический провайдер чанков** — реализация `net::ChunkSource`,
  отдающая плоские чанки из памяти (одна палитра, 0 блок-энтити): убирает
  диск/кэш реального мира из цикла измерения. Разрешён для bench **и для
  длинных заездов стриминга (100+ чанков, критерий M4.4)**. Парити от
  него не зависит (bench не в pipeline парити).

### Риски

1. **(а) Статическое разбиение регионов против окна видимости,
   пересекающего границу региона.** Разбиение чанков на регионы статично
   (§1), а окно игрока — квадрат ±R, который спокойно заходит за границу
   обоих регионов. Для M4 (позиции) это решается `Transfer`, но для
   **блоков в M5** нужны обновления состояния мира между регионами;
   Folia для таких случаев объединяет регионы **динамически**, а наша
   схема статическая. Расхождение договорённостей: решать к M5, в M4 не
