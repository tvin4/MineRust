Состояние: **не выполнялось владельцем**. Автоматически: `cargo test --workspace`
зелёный (net — 117 ok); ignored-прогон (г)
`cargo test -p parity --release --test entity_view_distance -- --ignored
--nocapture` на v3 — С3 на нашем сервере: геометрические remove **160.2–160.4**
блоков (ваниль **160.2**), возврат **159.8** в интервале из Шага 1.4
`[154.4, 160.2]`, максимум видимости 160.2 (ваниль 160.2), порядок ухода из мира
`remove_entities` → `player_info_remove` как в C1. Ниже — что посмотреть глазами
**двумя** клиентами 26.3 на одной машине.

Из известного по Шагу 6.3 (`docs/ARCH-M4.md` §6): при живом наблюдении другой
модель может «смазывать» поворот головы (байт `rotate_head`, остаток (ii)) и
получать редкие `entity_position_sync` (остаток (i)) — это **известные**
расхождения с ванилью, а не дефект живой проверки; жаловаться на них не нужно,
но наблюдения (плавность поворота, рывки при смене направления) — полезны для
решения владельца по (i)/(ii).

**После Шагов 7.1–7.3** сервер больше не шлёт spectator-константы: невидимость
(`set_entity_data` entity flags `0x20`) и режим 3 в Tab убраны, режим игрока —
`default_game_mode` сервера (у обычного запуска **0**, survival; параметра в
`server.toml` нет). Остатки (i)–(ii) выше к этому не относятся. Режим 3 в конфиге
стенда даёт только байты потока о других игроках: своих пакетов spectator-режима
(`player_abilities`, полёт) нет — если сервер запущен с `default_game_mode = 3`,
клиент останется без них (в обычном запуске это не встречается).


## Шаги (8 строк)

1. В `server.toml` `world_dir` — рабочий шаблон (у владельца v3
   `C:\MineRust-data\world-template-v3`); запустить `tools\run-server.bat`, ждать
   `listening` и `world warm-up finished: chunks ready to send N`.
2. Войти **первым** клиентом 26.3 на `localhost:25565` (view distance 10) —
   Multiplayer → Add Server. Дождаться прогрузки мира.
3. **Второй** клиент 26.3 на той же машине: отдельный рабочий каталог
   (`.minecraft`) или отдельный профиль лаунчера, тот же аккаунт — сервер offline,
   UUID по имени, второй вход не отклонится. **Fallback:** если лаунчер не даёт
   второй экземпляр, живой вход двух клиентов не получится — тогда одиночная
   проверка (шаги 4–7 по памяти/по одному клиенту невозможны) плюс ignored-тест
   (г) (два бота in-process с настоящими сокетами) и в отчёте явно написать, что
   живого входа двух клиентов не было.
4. Наблюдать: **другой игрок виден** — модель появляется на его координатах и
   плавно повторяет его движение при ходьбе (Position), при развороте — поворот
   (Rotation). С себя — модель не появляется (себя не видит).
5. **Tab** (список игроков) показывает **оба** имени (вход в Tab — `player_info_update`).
6. Разойтись/сойтись: уйти на **>160 блоков** (view distance 10 → радиус `10×16`)
   — модель другого **исчезает** (remove_entities); вернуться — **появляется**
   снова (add_entity) в пределах одного шага. Проверять по `F3` (координаты
   обоих).
7. Выйти одним клиентом из мира: у второго его модель пропадает **сначала**
   (remove_entities), затем уходит строка из Tab (player_info_remove). В логе
   сервера — **нет** `WARN`/`ERROR` и нет пачки `tick woke late` (единичный
   выброс при входе допустим). Если такая строка есть — прислать её целиком
   (`tick`, `late_ms`, `uptime_ms`, `players`) и **время входа** клиента: без
   пары «строка + момент входа» источник не определить (Шаг 7.4: при нуле
   игроков опозданий нет — 400 тиков, `late_max_ms = 0`).
8. Скриншот (мир + `F3`, желательно **Tab с двумя именами**) — в отчёт. Норма —
   «M4.5 ок»; иначе прислать лог (`net=debug`), координаты обоих, маршрут и
   скриншот.
