# tools/testclient/geometry — готовые dev_geometry-сцены (Шаг 16.0c)

Файлы для **ручной** проверки владельцем на нашем сервере: плавание у
поверхности, ползание под низким проёмом и waterlogged-блоки рядом с водой.
Каждый файл — список команд `setblock`/`fill` в формате dev-параметра
`dev_geometry` (Шаг 15 п.2). Сервер читает его при старте и пишет блоки в
**память** (`ChunkStore`) до привязки порта; мир на диске и шаблон v3 не
меняются.

**Эти параметры по умолчанию не включаются.** Ни один файл отсюда не
подключается в `server.toml` автоматически: включай по одному вручную и
выключай после проверки.

## Как включить

1. В своём `server.toml` (он не коммитится) добавь строки нужной сцены:

   ```toml
   dev_geometry  = "tools/testclient/geometry/pond.txt"
   spawn_override = "106,41,-31"
   ```

   `spawn_override` — целые `x,y,z`; клиент центрирует `x` и `z` (`+0.5`),
   поэтому `106,41,-31` в игре — это `(106.5, 41, -30.5)`. Оба отчёта должны
   быть заданы, иначе часть проверок выключена:

   ```toml
   # без него нет позы ползания (в логе `WARN no collision_report ...`)
   collision_report = 'E:\MineRust-data\reports\collision.json'
   # без него у наблюдателя НЕТ трещин (в логе `WARN no hardness_report ...`)
   hardness_report = 'E:\MineRust-data\reports\hardness.json'
   ```

   Как получить файлы (оба — команды тест-клиента, нужен запущенный клиент
   в мире и на земле; файлы пишутся вне репозитория):

   ```text
   {"cmd":"shapes","args":{"path":"E:/MineRust-data/reports/collision.json"}}
   {"cmd":"hardness","args":{"path":"E:/MineRust-data/reports/hardness.json"}}
   ```

   Команды отправляются в контрольный сокет клиента (Alice 25571), например
   `Invoke-TestCmd 25571 '{"cmd":"hardness","args":{"path":"..."}}'` из
   `tools/testclient/scenario-lib.ps1`. Ожидаемые размеры: `collision.json` —
   35723 состояния, 30144 непустых; `hardness.json` — 35723 состояния,
   116 несокрушимых.

   **Трещин нет в creative.** Таймер и `block_destruction` работают только в
   survival: в creative клиент ломает блок мгновенно, сервер шлёт только
   `block_update`, стадий нет (Шаг 14c/16a).

2. Перезапусти сервер (`tools\run-server.bat`) и зайди двумя клиентами
   (`tools\run-two-clients.bat`, Alice 25571 / Bob 25572).

3. Смотри, что видит B у A:

   ```json
   {"id":1,"cmd":"observe","args":{"player":"Bob"}}
   ```

   (команда отправляется в сокет Alice 25571; ответ — поза `pose`,
   `isSwimming`, `isSprinting`, `isCrouching`, координаты и блок у ног/головы).

4. После проверки **убери** `dev_geometry`/`spawn_override` из `server.toml`.

## Сцены

### `pond.txt` — пруд (плавание у поверхности)

9×9 каменный бассейн, вода y=37..41 (поверхность на y=41). Спавн в
поверхности воды.

```toml
dev_geometry  = "tools/testclient/geometry/pond.txt"
spawn_override = "106,41,-31"
```

Игрок падает в воду. Гистерезис входа (Шаг 15, §2.1): чтобы поплыть, зажми
`up` + `sprint`, глаза уйдут под воду — поза станет `SWIMMING`. Отпусти
`sprint` — поза (`3`) держится, пока ноги в воде, флаг гаснет примерно на одно
событие позже; выйди на поверхность — `STANDING`.

**Ожидание у B (ванильная таблица, `docs/SWIMMING.md` §2.1):**

| ноги в воде | sprint | sneak | flags (B) | pose (B) |
|---|---|---|---|---|
| нет | нет | нет | `0x00` | 0 STANDING |
| нет | да | нет | `0x08` | 0 STANDING |
| нет | нет | да | `0x02` | 5 CROUCHING |
| да | нет | нет | `0x00` (после отпускания спринта ещё одно событие `0x10`) | 0 |
| да | да | нет | `0x18` (при отпускании → `0x10` → `0x00`) | 3 SWIMMING |
| да | нет | да | `0x02` | 5 CROUCHING |

Регрессия P2 (живой тест 16.11, фикс `c066c1a`): при **всплытии с зажатыми
up+sprint+jump** бит плавания не должен щёлкать на каждой границе блока —
анимация держится всю дорогу и гаснет честно при выходе на поверхность.

### `crawl.txt` — ползание (проём 1 блок и 1.5 блока)

Платформа y=199..200 (feet y=201) с двумя крытыми коридорами восточнее
(`+x`): каменная крыша на y=202 (проём **1.0**) при `z≈-46.5` и крыша из
`stone_slab[type=top]` (проём **1.5**) при `z≈-41.5`. Первые три клетки
подхода — без крыши.

```toml
dev_geometry  = "tools/testclient/geometry/crawl.txt"
spawn_override = "56,201,-47"
```

Игрок входит в открытом подходе. Повернись на восток (`+x`) и иди вперёд в
каменный коридор; затем отойди на юг (`z≈-41.5`) и войди в коридор с плитой.

**Ожидание у B (ванильная таблица, `docs/SWIMMING.md` §5):**

| свободное место над головой | pose (B) | flags (B) | hitbox |
|---|---|---|---|
| `< 1.5` (каменная крыша, 1.0) | 3 SWIMMING (ползание) | `0x00` | 0.6 |
| `1.5 .. 1.8` (плита, 1.5) | 5 CROUCHING | `0x02` | 1.5 |
| `>= 1.8` (открыто) | 0 STANDING | по вводу (sneak/sprint) | 1.8 |

Важно (§5): поза принуждается по месту над **текущей** позицией, а не «по
намерению войти». У нас нет модели коллизий, поэтому в низкий проём упирается
клиент, а сервер только понижает позу, когда ноги уже под крышей.

### `waterlogged.txt` — waterlogged-ступеньки/плиты/забор рядом с водой

Платформа y=200, вода на ней (y=201, поверхность воды), в воде четыре
waterlogged-блока на уровне пола (y=200): `stone_slab[type=top]`,
`stone_slab[type=bottom]`, `oak_stairs`, `oak_fence`.

```toml
dev_geometry  = "tools/testclient/geometry/waterlogged.txt"
spawn_override = "92,201,-32"
```

Игрок входит на сухом южном краю; иди на север (`-z`) в воду и на блоки.

**Ожидание у B (`docs/SWIMMING.md` §2.1/§2.2):**

- Вода у ног (игрок **внутри** waterlogged-блока или просто в воде) считается
  водой (`8/9`): при спринте → поза 3 SWIMMING, flags `0x18`; в покое → 0.
- Блок, на котором игрок **стоит сверху**, водой у ног не считается (ноги в
  клетке — воздух): поза по вводу.
- `oak_stairs[waterlogged=true]`, `oak_fence[waterlogged=true]`,
  `stone_slab[type=top/bottom,waterlogged=true]` — те же, что в сетке S10
  (`G4-wl-*`), где slab-top/stairs совпали с ванилью 141/141.

**Известные долги** (могут дать расхождение с ванилью, `docs/SWIMMING.md`
§2.2):

- **Нет симуляции жидкости.** В `G4-wl-slab-bottom` ваниль разнесла воду на
  поверхность платформы (`water level 7/6/5`), у нас эта клетка остаётся
  `air`; отсюда 4 расхождения. В этой сцене вода задана явно командой
  `fill ... water`, поэтому у нас она есть в клетках, куда мы её написали, но
  «сама» не растекается.
- **Нет модели коллизий.** В `G4-wl-fence` ваниль не меняет позу при зажатом
  sneak (тело перекрыто столбом забора), наш сервер включает `CROUCHING`
  (`0x02`) — 6 расхождений. Воспроизвести нельзя без модели коллизий.

## Проверка синтаксиса

Файлы парсятся тем же кодом, что и dev_geometry сервера
(`crates/server/src/geometry.rs`); тест
`shipped_dev_geometry_files_parse` (в `geometry.rs`) прогоняет `load()` по
каждому файлу этого каталога, поэтому опечатка в команде валит `cargo test`.
Разрешение состояний (что имена и свойства существуют) требует
`reports/blocks.json` и проверяется только на живом сервере.
